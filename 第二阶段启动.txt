============================================================
一、工作目录与目标
============================================================

系统目录：本文件所在目录，也就是包含 src/cli.py、config/system.toml 和 runs/agent-10 的目录。
当前位置参考：<本文件所在目录>

固定评测批次：agent-10

应有裁判包：124 个，文件名从 K001.md 开始，但编号可能不连续，以实际文件为准。

你的最终交付：

============================================================
二、裁判资格与独立身份
============================================================

1. 正式裁判应是没有参与 agent-10 第一阶段作答的模型，并尽量与其他裁判来自不同厂商。
2. 如果你或同一产品中的当前模型已经作为候选参加第一阶段，不要提交正式裁判票；请明确报告身份冲突。
3. 使用真实的 judge_id，格式为 judge-产品-模型，例如 judge-example-product-example-model。
   judge_id 只能含字母、数字、点、下划线和连字符，不要包含斜杠。
   不知道精确模型版本时使用 judge-产品-current-agent，并在完成标记中注明版本未知。
4. 不得冒用其他模型身份，不得使用其他裁判的 inbox 目录，不得覆盖其他裁判的票。

============================================================
三、严格的信息边界
============================================================

只允许读取：
- 本文件；
- runs/agent-10/judgments/packets/K*.md；
- 你自己的 inbox/<judge_id>/ 输出。

不要读取：
- runs/agent-10/raw/、normalized/；

- runs/agent-10/judgments/queue*、verdicts.jsonl、votes/；

- reports/ 中任何已有报告或分数。

不得联网搜索答案，不得运行被测项目或复现测试，不得安装依赖。
只根据裁判包内的声明与代码进行静态技术判断。代码不足时选 unsure，不要索要更多代码。

============================================================
四、逐包独立裁决并立即保存
============================================================

按文件名顺序逐一处理所有实际存在的 K*.md。每完成一条立即写入对应 JSON，不要等到最后一起保存。

完整阅读每个裁判包，并严格服从包内的 judge_v1 提示。你只回答：
“这条声明描述的问题，在所给代码里真实存在吗？”

 verdict 只能取：
- valid：声明给出的触发条件与后果确实成立；
- invalid：声明事实有误、前提不成立、后果被夸大，或代码已有防护；
- unsure：代码不足、依赖未知或无法可靠确定。

注意：
- 缺陷不严重不等于 invalid。
- 不要因为多个模型可能提出过它就判 valid。
- 不要补充新缺陷，不要评价答案文采，不要猜测来源。
- reason 用一句话写出具体代码依据，不超过 60 字，不要只复述标题。
- severity_ok 必须是 true 或 false；只有声明的严重度档位偏差超过一级时才填 false。
- 宁可选 unsure，也不要猜。

每份文件只包含一个合法 JSON 对象，不要 Markdown 围栏，不要任何额外文字：

{"verdict":"valid","reason":"这里填写具体依据","severity_ok":true}

保存路径：
runs/agent-10/judgments/inbox/<judge_id>/<cluster_id>.json

如果某份输出已存在，只有在它属于当前 judge_id 且你要续跑时才可以读取；格式不完整时补正，不得凭记忆跳过实质审查。
中断后重新执行本文件，从缺失或不完整的 cluster_id 继续。

============================================================

全部裁判包处理完后，使用可用的 Python 校验：

2. 应有 124 份裁决，不得漏项或多项；
3. 每份 JSON 均可解析，且只含一个对象；
4. verdict 只能是 valid、invalid、unsure；
5. reason 是非空字符串且不超过 60 字；
6. severity_ok 是布尔值；
7. 任一检查失败时，先修正你自己的输出，不得导入不完整裁判票。

Python 优先使用当前环境中的 python。若 python 无法运行，可尝试：

或 python3

============================================================
六、导入裁判票，但不要汇总排名
============================================================

只有 124 份裁决全部通过校验后，才执行：

<PYTHON> src/cli.py votes agent-10 "<judge_id>" "runs/agent-10/judgments/inbox/<judge_id>"

命令应报告收到 124 张票。少于 124 时停止并检查，不得声称完成。

不要执行 verdicts、score、report 或 all。
这些命令会把当前已到的票用于正式裁决；在其他裁判尚未完成时执行，会造成阶段性分数被误当成最终结果。

导入成功后，在自己的 inbox 目录创建 judge_complete.json，内容包括：
- judge_id；
- run_id = agent-10；
- packet_count = 124；
- valid、invalid、unsure 的实际数量；
- completed_at，使用真实本地时间；
- 精确模型版本未知时注明 model_version_unknown = true。
