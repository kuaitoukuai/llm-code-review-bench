# 07 评分规则

> 评分是这套系统里唯一"必须做价值判断"的地方。
> 这一篇把所有主观选择摊开写，包括它们的代价。

---

## 一、两种评分哲学

| | 绝对分（v0.1） | 率化分（v0.2+） |
|---|---|---|
| 公式 | Σ(命中×权重) − 误报×系数 + 独到加成 | 100×(0.7Rw+0.2P+0.1C) − 2F − 4Fh − 5T + U |
| 需要什么 | 只需要本轮数据 | 需要**答案集**（分母） |
| 奖励什么 | 发现得多、发现得重 | 发现得多 **且** 报得准 |
| 能不能跨 run 比 | ❌ 不能（权重变了就不可比） | ✅ 能（分母固定） |
| 什么时候能用 | 冷启动 | bank 覆盖 ≥ 0.8 |
| 最大风险 | "多报多得"——报 20 条蒙 3 条也能拿分 | 分母虚高——把模型并集当真相 |

**两套都保留，并列展示。** 不是优柔寡断，是因为它们回答的是两个不同问题：绝对分回答"这次谁贡献大"，率化分回答"这个模型有多可靠"。

## 二、冷启动公式（阶段 A）

### 2.1 公式

```
原始分 = Σ(命中 × 严重度权重) − 误报数 × 0.5 + Σ(独到命中 × 权重)
终　分 = 原始分 × 时间系数
```

### 2.2 严重度权重

| 严重度 | v0.1 现值 | 本方案建议 | 理由 |
|---|---|---|---|
| P0 | 5.0 | **8.0** | 数据损坏/安全漏洞的价值应远高于"多找几个小问题" |
| P1 | 3.0 | **4.0** | 略微上调，保持与 P0 的 2:1 关系 |
| P2 | 2.0 | **2.0** | 不变 |
| P3 | 1.0 | **0**（仅记录） | 风格类问题判定方差最大，给分等于给噪声加权 |

调整为 8/4/2/0 之后，一条 P0 等于四条 P2，与"修一个 P0 的时间成本"大致相当。

### 2.3 三个刻意的选择

| 选择 | 值 | 为什么 | 代价 |
|---|---|---|---|
| 误报系数 | 0.5（不是 1） | 漏掉真 bug 的代价高于多看一个假的 | 容忍一定噪声 |
| 独到加成 | 2.0（不是 1.5） | 对抗"多数票杀掉独到发现" | 幻觉条目也可能被加分（靠人工复核拦） |
| 最少条数 | 3（不足按误报补） | 堵死"一条不报"的最优策略 | 干净代码上被迫编造 |

### 2.4 时间系数

```
ratio = 实际耗时 / std_seconds（该项目固定基准）
grace = 2.0
if ratio <= grace:       系数 = 1.0
else:                    系数 = 1 − min(0.05, 0.05 × (ratio − grace) / grace)
```

即：超过基准 2 倍才开始扣，最多扣 5%。

**为什么用固定基准而不是全局中位数**（v0.1 的做法）：

| | 全局中位数 | 固定基准 |
|---|---|---|
| 新模型加入时 | 中位数变化 → 所有老模型分数变动 | 不变 |
| 可比性 | 只在同一批候选内可比 | 跨批次可比 |
| 公平性 | 对大项目不利（拉高中位数） | 按项目体量分配预算 |

这是本方案对 v0.1 的一处**修正**。代价是 `std_seconds` 要人工估，估不准会导致扣分失真——所以 `04` 里给了估算口径（300/600/900）。

## 三、率化公式（阶段 B）

### 3.1 七个量

| 符号 | 名称 | 定义 |
|---|---|---|
| `Rw` | 加权召回率 | 该候选命中的 issue 权重和 ÷ bank 中 active issue 的总权重 |
| `P` | 精确率 | confirmed ÷ (confirmed + rejected + out_of_scope) |
| `C` | 严重度校准 | 每条：与 `real_sev` 完全一致 = 1，差一级 = 0.5，差更多 = 0；取平均 |
| `F` | 普通误报数 | `rejected` 且 `real_sev ≤ P2` 的条数 |
| `Fh` | 高严重度假报数 | 提交者声称 P0/P1，最终 `rejected` 的条数 |
| `T` | 时间消耗比 | 实际耗时 ÷ `std_seconds`，封顶 1.0 |
| `U` | 独到加成 | 见 3.3 |

### 3.2 公式

```
rate_score = 100 × (0.7×Rw + 0.2×P + 0.1×C) − 2×F − 4×Fh − 5×T + U
```

权重含义：**召回 70% > 精确 20% > 严重度判断 10%**。

这个配比反映的是 R3 的优先级："重要问题发现能力 ＞ 报告可信度 ＞ 严重度判断 ＞ 速度"。如果你更在意"别报假的"，把 0.7/0.2 改成 0.6/0.3 即可，重算不用重跑。

### 3.3 独到加成 U

```
U = Σ(该候选独到命中的 issue 权重 × 系数)
系数：1 个发现者 → 1.0（额外加一份权重，等价翻倍）
      2 个发现者 → 0.3
      ≥3 个发现者 → 0
```

注意这里和 `06` 的 2.0/1.3/1.0 是同一件事的两种写法：

| 发现者数 | 总系数 | 在率化公式里的额外加成 |
|---|---|---|
| 1 | 2.0 | +1.0 × 权重 |
| 2 | 1.3 | +0.3 × 权重 |
| ≥3 | 1.0 | +0 |

`U` 有上限：每个项目最多 +2 分，防止"靠独到发现刷榜"。

### 3.4 什么时候切到阶段 B

三个条件同时满足：

1. `bank` 中 `active` 且 `verdict=confirmed` 的条目 ≥ 20
2. bank 覆盖率 ≥ 0.8（即 80% 的 claim 能撞上库）
3. 至少有一轮做过裁判或人工裁决（不能全是 `inferred`）

不满足时，`rate_score` 字段输出 `null`，报告里显示"题库未成型"。

## 四、同一批数据，两套公式给出的差距完全不同

这是双轨制存在的实证理由。构造一个例子（v0.2 权重 8/4/2/0）：

**候选 A（少而精）**：报 2 条，全中——1 条 P0，1 条 P1，误报 0，耗时 500s（基准 600）

**候选 B（多而杂）**：报 9 条，中 6 条（1 条 P0 + 1 条 P1 + 4 条 P3），误报 3（其中 2 条声称 P0），耗时 700s

### 绝对分

```
A = (8 + 4) − 0 + 独到(0) = 12
B = (8 + 4 + 0×4) − 3×0.5 − 2×2(Fh 额外) = 12 − 1.5 − 4 = 6.5
```

→ **A 赢**（12 vs 6.5）

### 率化分（假设 bank 总权重 40）

```
A: Rw = 12/40 = 0.30   P = 2/2 = 1.00   C = 1.0
   = 100×(0.21 + 0.20 + 0.10) = 51.0 − 0 − 5×0.83 = 46.9

B: Rw = 12/40 = 0.30   P = 6/9 = 0.67   C = 0.7
   = 100×(0.21 + 0.134 + 0.07) = 41.4 − 2×3 − 4×2 − 5×1.0 = 41.4 − 6 − 8 − 5 = 22.4
```

→ **A 大幅赢**（46.9 vs 22.4）

### 结论

两套公式在这组数据上方向一致，但**差距不同**：绝对分差 5.5，率化分差 24.5。

方向一致是好事，说明公式没有系统性打架。差距不同也是好事——率化分对"虚报高严重度"的惩罚更重，因为 `Fh×4` 那一项。

**如果两套公式给出相反的排序，说明数据有问题**，通常是：

- bank 分母太小（刚建库就切率化分）
- 或者候选之间报的条目数量差异极大（1 条 vs 20 条）

遇到这种情况，以绝对分为准，并在报告里注明"率化分不稳定"。

## 五、P3 为什么建议不计分

P3 是"可维护性、命名、注释、重复代码"。三个理由：

1. **判定方差最大**。同一个命名，三个裁判可能给 P2/P3/P3——它本身就不是一个稳定的信号。
2. **不设上限会淹没主信号**。一个模型可以报 12 条全是 P3，稳稳拿分。
3. **对你的实际价值最低**。你要的是"能拿去修的 bug"，不是"这段代码可以更优雅"。

保留记录但计 0 分，是为了让报告里还能看到"这个模型倾向于报风格问题"——这本身是有信息量的（说明它谨慎但不够深入）。

## 六、时间与 Token

### 6.1 时间的三个用途

| 用途 | 进主分吗 | 权重 |
|---|---|---|
| 超时扣分 | ✅ | 最多 5 分（率化）/ 5%（绝对） |
| 效率排序 | ❌ | 单独一列"每分钟有效权重" |
| 超时标记 | ❌ | `status=timeout`，报告里标灰 |

**效率轴的计算**：

```
效率 = 加权命中分 / (耗时分钟)
```

这个值不进总分，但值得单列。因为"10 分钟找到 3 个 P1"和"90 分钟找到 4 个 P1"是两种完全不同的能力，前者更适合日常用。

### 6.2 Token 只展示

三个原因：

1. 各产品口径不一致（有的算缓存，有的不算）
2. 输入 token 尤其不可比（产品侧可能塞了系统提示/索引）
3. 拿不到精确值时填 NA，会破坏排序

所以：`token_in` / `token_out` 进 `run_logs.jsonl`，报告里单独一节，**不进任何公式**。

## 七、并列与噪声

### 7.1 并列判定

| 分数类型 | 并列阈值 | 理由 |
|---|---|---|
| 绝对分 | 分差 < 2 | 约等于"一条 P2"的分值，低于这个差异无意义 |
| 率化分 | 分差 < 3 | 约等于一个误报+一点时间扣分 |

并列时报告怎么写：

```
第 1 名（并列）  workbuddy/claude-sonnet-5.5   46.9
第 1 名（并列）  kimi/kimi-k2.5                45.2   ← 分差 1.7 < 2，判并列
第 3 名          kimicode/glm-5.5              38.1
```

**不要写成 1、2、3、4。** 10 个项目的样本量支撑不了小数点后的排序。

### 7.2 噪声

同一候选同一项目跑两次，分差在 10% 以内视为噪声（源自公开实测：三次重复之间 F2 中位波动 2.6 分，个别配置 7.5 分）。

报告里的用法：

```
若 |score_A − score_B| < 10% × max(score_A, score_B) → 标注"差距在噪声范围内"
```

### 7.3 什么时候必须做 repeat

| 场景 | 是否 repeat |
|---|---|
| 首轮摸流程 | 否（1 次够了） |
| 前两名分差 < 10% | **是**（做 3 次取中位数） |
| 要对外发布结论 | **是** |
| 只想知道"哪个明显更强" | 否 |

## 八、敏感性检查

只做一件事，但必须做：**把 `uncertain` 按两种极端各算一遍，看排名是否稳定。**

```
方案 1：uncertain 全部算命中 → 重算排名
方案 2：uncertain 全部算误报 → 重算排名
比较三份排名（基准 / 方案1 / 方案2）
```

三种结果：

| 结果 | 含义 | 怎么写报告 |
|---|---|---|
| 三份排名一致 | 结论稳健 | 正常发布 |
| 只有中段变化 | 头部稳，腰部不稳 | 只报头部，腰部标"未定" |
| 头部变化 | 结论不稳 | 必须人工裁决所有 uncertain，再重算 |

这一步的意义：**让你知道自己的结论有多脆弱**。如果 5 条 uncertain 就能翻转第一名，那这个第一名不值得写进 PPT。

## 十、一句话总结

**冷启动看绝对分，题库成型看率化分，两套并列，谁也别假装自己精确。**

排名的可信度不来自小数位，来自：证据级别标注、并列判定、噪声阈值、敏感性检查，这四件小事。
