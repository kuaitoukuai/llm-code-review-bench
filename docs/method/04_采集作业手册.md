# 04 采集作业手册

> 这是全套方案里唯一"必须你亲手做"的部分。
> 目标：**10 个项目、4 个候选、2 小时内采完，且不因为手滑毁掉可比性。**

---

## 一、为什么采集不能全自动（现在还不能）

三个现实约束：

1. **Kimi Code / WorkBuddy 都是产品形态**，不是裸 API。同一个模型在不同产品里工具链不同，走 API 采到的结果代表不了产品。
2. **要测的是"组合能力"**（R4 明确不区分产品与模型），所以必须在产品界面里跑。
3. **token 与耗时**只有产品侧才准，API 侧拿到的是另一套账。

所以 v0.1–v1.0 的采集都是"人肉搬运 + 程序记账"。v0.3 再做 API 通道，作为对照，不作为主通道。

## 二、前置准备（一次性，约 40 分钟）

### 2.1 建题库：从 30 个候选里挑 10 个

```bash
python src/cli.py scan "<你的项目目录>"
python src/cli.py scan "<另一个项目目录>"
```

输出 `config/projects.suggested.toml`，按四个维度打分：

| 维度 | 权重 | 判据 |
|---|---|---|
| 有 git 历史 | 高 | 能取 commit，冻结可追溯 |
| 体量合适 | 高 | 500–8000 行有效代码（太小没东西可查，太大超时） |
| 有测试 | 中 | 有测试的项目，埋点验证才有意义 |
| 近期改过 | 高 | 三个月内动过的代码，问题还"活着" |

**挑选原则**（比分数重要）：

- **不要挑你最熟的项目。** 你熟到能背下来的地方，你也会先发现，模型的独到发现就没意义了。
- **不要挑全是生成代码的项目。** 机器写的代码问题模式单一，区分度低。
- **要有一个"脏"项目。** 赶工出来的、有技术债的，这类项目的问题分布最接近真实。
- **要有一个"干净"项目。** 用来测幻觉——在没 bug 的地方硬报，是最能拉开差距的场景。

### 2.2 填 `projects.toml`

```toml
[[project]]
id = "t05-shadow"
path = "<你的项目路径>"
target_dirs = ["apps/api/src", "apps/web/src"]
exclude = ["**/node_modules/**", "**/dist/**"]
max_file_lines = 800
std_seconds = 600
enabled = true
```

三个字段最容易填错：

| 字段 | 填错的后果 | 怎么填 |
|---|---|---|
| `target_dirs` | 模型跑去读 `node_modules`，单项目耗时从 8 分钟变 40 分钟 | 只填**业务源码**目录，不填根目录 |
| `max_file_lines` | 单文件 3000 行，prompt 直接爆上下文 | 600–800，超长文件自动跳过 |
| `std_seconds` | 时间扣分失真 | 按项目体量估：小型 300，中型 600，大型 900 |

### 2.3 填 `candidates.toml`

首轮建议 4 个，覆盖至少 3 个 vendor：

```toml
[[candidate]]
id = "kimi/kimi-k2.5"
product = "Kimi Code"
model = "kimi-k2.5"
vendor = "moonshot"
enabled = true

[[candidate]]
id = "workbuddy/claude-sonnet-5.5"
product = "WorkBuddy"
model = "claude-sonnet-5.5"
vendor = "anthropic"
enabled = true

[[candidate]]
id = "workbuddy/deepseek-v4.1-flash"
product = "WorkBuddy"
model = "deepseek-v4.1-flash"
vendor = "deepseek"
enabled = true

[[candidate]]
id = "kimicode/glm-5.5"
product = "Kimi Code"
model = "glm-5.5"
vendor = "zhipu"
enabled = true
```

**vendor 必须填对**。它决定"支持度去重"和"裁判跨族"，填错等于把三家当成一家。

### 2.4 冻结题库

```bash
python src/cli.py new-run r01
python src/cli.py task t05-shadow
python src/cli.py task t06-xxx
...
```

`task` 会生成 `tasks/<task>/prompt.md`——**已经拼好全部代码的完整提示词**，打开全选复制即可。

同时写入 `meta.json`：

```json
{"project":"t05-shadow","commit":"d735825","created":"2026-11-14T02:05:00",
 "file_count":42,"total_lines":6830,"dataset_version":"dataset_v1"}
```

> ⚠️ **一旦开始采集，题库就冻结。** 中途改 `target_dirs` 或换文件，前面采的全部作废。

## 三、单项目 10 分钟预算

| 阶段 | 时间 | 动作 | 失败表现 |
|---|---|---|---|
| 贴提示词 | 0:00–0:30 | 全选复制 `prompt.md` → 粘贴 → 回车 | 粘贴不全（检查首尾行） |
| 模型思考 | 0:30–5:00 | 等 | 超过 8 分钟 → 记为 `slow` |
| 输出阶段 | 5:00–8:00 | 等 JSON 出完 | 输出被截断 → 重跑 |
| 保存回复 | 8:00–9:00 | 全选复制 → 存 `out.md` | 复制到一半 → 检查 JSON 完整性 |
| 登记 | 9:00–10:00 | `done` 命令 + token | token 拿不到 → 填 NA |

**硬边界**：单项目 15 分钟（`std_seconds` 的 1.5 倍）。到点没出完，保存已有部分，记 `status=timeout`，继续下一个。

理由：一个项目拖 40 分钟，10 个项目就变成 6 小时，2 小时约束直接崩。而且超时的那部分输出质量通常也差。

## 四、逐步操作（命令级）

### 4.1 开始一个项目

```bash
python src/cli.py start r01 kimi/kimi-k2.5 t05-shadow
```

输出：

```
[START] r01 kimi/kimi-k2.5 t05-shadow r1
        time: 2026-11-14T02:12:03+08:00
        raw : runs/r01/raw/kimi/kimi-k2.5/t05-shadow/r1.md
```

> 计时从这条命令开始。**先 start 再贴提示词**，否则耗时偏短。

### 4.2 贴提示词

打开 `tasks/t05-shadow/prompt.md`：

- `Ctrl+A` 全选
- `Ctrl+C`
- 粘贴到 Kimi Code / WorkBuddy 对话框
- 确认输入框底部显示的字数 ≈ 文件大小（差太多说明粘贴不全）

**不要做任何修改。** 加一句"请仔细检查"就毁掉了可比性。

### 4.3 保存回复

模型输出完成后：

1. 全选回复内容
2. 粘贴到 `runs/r01/raw/kimi/kimi-k2.5/t05-shadow/r1.md`
3. 检查：文件是否以 `[` 开头、以 `]` 结尾（或含 ```json 块）

**保存原始文本，不要手工清洗。** 归一化脚本会处理格式，手工改动会让"原始层不可变"失效。

### 4.4 登记

```bash
python src/cli.py done r01 kimi/kimi-k2.5 t05-shadow \
  --from runs/r01/raw/kimi/kimi-k2.5/t05-shadow/r1.md \
  --token-in 45000 --token-out 3200
```

token 拿不到就留空：

```bash
python src/cli.py done r01 kimi/kimi-k2.5 t05-shadow --from out.md
```

`done` 会写 `run_logs.jsonl`（起止时间、墙钟耗时、token、status），并把 `r1.md` 复制进 raw 目录并置只读。

### 4.5 换下一个

```bash
python src/cli.py start r01 kimi/kimi-k2.5 t06-xxx
```

> **建议按"候选"而不是按"项目"循环。** 同一个产品里连续跑完 10 个项目，可以少切换界面、少登录，切换成本最低。

## 五、防跑偏：提示词末尾的护栏

`review_v1/v2` 里已经写了"只报告缺陷""最多 12 条"，但实际跑下来还需要三条护栏（建议写进 `review_v3`）：

```
# 范围限制（新增）

1. 只审查上文提供的代码。不要读工作区里的其他文件，不要执行任何命令，
   不要运行测试或编译，不要访问 node_modules / dist / build / 日志目录。
2. 如果某个文件的代码不完整或被截断，不要猜测缺失部分，只在完整可见的
   范围内找问题。
3. 每个项目最多报 8 条。按你判断的严重度排序，先报最严重的。
```

三条护栏的作用：

| 护栏 | 防什么 | 实测效果 |
|---|---|---|
| 禁读其他文件 | 模型自己去 grep 整个仓库，耗时从 8 分钟涨到 40 分钟 | 耗时稳定 |
| 禁跑命令 | 触发编译/测试，几分钟就没了 | 耗时稳定，且避免环境污染 |
| 最多 8 条 | 模型凑数刷满 12 条，误报率飙升 | 精度提升，召回基本不变 |

## 六、两小时时间表

假设 10 个项目、4 个候选，共 40 次采集。

| 时段 | 内容 | 累计 |
|---|---|---|
| 0:00–0:10 | 准备：打开 4 个产品、登录、打开 `prompt.md` 目录 | 10 min |
| 0:10–1:50 | 候选 A 的 10 个项目（每个 10 分钟） | 110 min |
| 1:50–2:00 | 登记核对、补漏 | 120 min |

**这只跑完 1 个候选。** 4 个候选 × 2 小时 = 8 小时，一天跑不完。

所以真实排法是**分三天，每天一个候选**：

| 天 | 内容 | 耗时 |
|---|---|---|
| D1 | 候选 A：10 个项目 | 2 h |
| D2 | 候选 B：10 个项目 | 2 h |
| D3 | 候选 C + D：各 10 个项目 | 4 h |
| D4 | 归一化 + 聚类 + 裁判包 + 人工复核 | 2 h |

**"2 小时"约束的正确理解**：单模型 2 小时内跑完 10 个项目。不是"整套评测 2 小时"。

## 七、采集期的七个故障

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | 输出不是 JSON，是一段散文 | 模型没遵守格式 | 整份作废，重跑；连续两次则换候选 |
| 2 | JSON 被截断（结尾缺 `]`） | 输出长度限制 | 重跑并降低"最多 8 条"；仍失败则记 `truncated` |
| 3 | 报的行号全部偏移 | 模型数错了代码块的行号 | `normalize` 会校验；偏移 >5 行整条拒收 |
| 4 | 报的文件名不存在 | 幻觉路径 | 拒收，计入 `_issues.jsonl` |
| 5 | 模型说"我无法访问该文件" | 产品侧权限/上下文限制 | 记 `blocked`，该组合不参与排名 |
| 6 | 同一项目两次结果差很多 | 模型有随机性 | 正常。首轮接受，S3 判据里抽检 |
| 7 | token 显示为"——" | 产品不暴露 | 填 NA，成本轴留空，不影响主分 |

每次故障都记进 `run_logs.jsonl` 的 `status`，月末统计"哪家产品最不稳定"——这本身就是一个有价值的结论。

## 八、采集质量的三个自检

采完一个候选后立刻做，不要等到全部采完：

```bash
python src/cli.py status r01
```

输出示意：

```
run r01  2026-11-14
  candidates: 4   tasks: 10   expected: 40   collected: 10
  [kimi/kimi-k2.5]        10/10  ok=9  timeout=1
  [workbuddy/claude-...]   0/10
```

三项自检：

| 检查 | 合格线 | 不合格怎么办 |
|---|---|---|
| 完成率 | ≥ 90%（40 次里至少 36 次 ok） | 补跑缺失的 |
| 解析率 | `normalize` 后拒收率 ≤ 15% | 拒收率过高说明提示词或模型有问题，先看 `_issues.jsonl` |
| 条数分布 | 每个候选平均 4–10 条 | 平均 <2 条 → 该模型过于保守或提示词太严；平均 >11 条 → 在凑数 |

**条数分布是最灵敏的信号。** 一个候选如果平均只报 1.5 条，要么它真的谨慎（好事），要么它没看懂代码（坏事）。看两条样本就能分辨。

## 九、采完之后的 90 分钟

```bash
python src/cli.py all r01
```

内部顺序：`normalize → cluster → packets → score → report`。

`all` 会在 `packets` 后停一下——它需要裁判票才能继续。两条路：

**路线 A：做裁判（推荐，证据硬）**

```bash
# 1. 把 packets/ 下的包逐个发给裁判模型（不参赛的、不同厂商的）
# 2. 每个回答存成 <cluster_id>.json
python src/cli.py votes r01 judge-claude runs/r01/judgments/votes/judge-claude
python src/cli.py votes r01 judge-glm   runs/r01/judgments/votes/judge-glm
python src/cli.py verdicts r01
python src/cli.py score r01 && python src/cli.py report r01
```

**路线 B：不做裁判（快，证据软）**

```bash
python src/cli.py score r01 && python src/cli.py report r01
```

走 B 路线时，只有"多家提出"的条目会被判为 `inferred_confirmed`，独到发现全部进人工队列。报告里证据强度那一列会大面积显示"弱"，这是诚实的表现，不是 bug。
