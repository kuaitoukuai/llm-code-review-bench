# 09 实施路线图

> 从 v0.1 到 v1.0，一共 12 张任务卡。
> 每张卡给出：改哪个文件、加什么接口、验收标准、工时。可以直接当 issue 用。

---

## 一、现状盘点

v0.1 已经有的（不用重做）：

| 能力 | 位置 | 状态 |
|---|---|---|
| 目录扫描与打分 | `pipeline.scan_projects` | ✅ |
| 题库冻结（files.jsonl + sha1 + prompt.md） | `pipeline.build_task` | ✅ |
| 计时与登记 | `session_start/done` | ✅ |
| 归一化 + 字段校验 + 拒收 | `pipeline.normalize` | ✅ |
| 聚类（文件+行号+标识符） | `pipeline.cluster` | ✅ |
| 匿名（pool/origin 分离） | `pipeline.cluster` | ✅ |
| 裁判包（一条一包，无来源无支持度） | `pipeline.make_packets` | ✅ |
| 裁判票回收 | `collect_votes` | ✅ |
| 裁决汇总 + 人工队列 | `adjudicate` | ✅ |
| 执行复现通道 | `execute_reproductions` | ✅ |
| 绝对分计分 | `pipeline.score` | ✅ |
| 报告（md + csv + 散点 html） | `report.build_report` | ✅ |
| 16 个命令 | `cli.py` | ✅ |

v0.1 缺的（本方案要补）：

| 缺口 | 影响 | 对应任务卡 |
|---|---|---|
| `evidence` 字段 | 无法核验"引用的代码是否真实存在" | T01 |
| 盐哈希 ID | 顺序 ID 可推断、跨 run 不稳定 | T02 |
| 六类裁决标签 | 只有 confirmed/rejected/pending，无法表达 out_of_scope | T03 |
| 高严重度假报惩罚 | 虚报 P0 与虚报 P2 同罚 | T03 |
| 顺序双评 | 位置偏差未剔除 | T04 |
| 埋点题库 | recall 没有真分母 | T05 |
| 并列判定 | 1.7 分差也排出名次 | T06 |
| 沉淀题库 | 加新模型必须重跑全部裁决 | T09–T10 |
| 率化分 | 跨 run 不可比 | T11 |
| 趋势 / 待修清单 | 报告只能看单次 | T12 |

## 二、v0.2 任务卡（让分数站得住）

### T01 · 加 `evidence` 字段并强制核验

| 项 | 内容 |
|---|---|
| **目标** | 每条 claim 必须引用真实代码片段，杜绝幻觉行号 |
| **改** | `prompts/review_v3.md`（新）｜`core.py`（`evidence_in_code`）｜`pipeline.normalize`（校验）｜`config/system.toml`（`chars.evidence = 60`） |
| **接口** | `core.evidence_in_code(text, file_lines, line, window=5) -> bool` |
| **实现要点** | 去空白、统一引号、允许 3 处字符差异；匹配窗口 `line ± 5` |
| **验收** | ① 构造 10 条带假 evidence 的 claim，全部被拒 ② 真实 claim 的误拒率 < 5% |
| **工时** | 0.5 天 |
| **风险** | 模型可能把代码复制错一个字，导致整条被拒 → 用宽松匹配（Levenshtein ≤3） |

### T02 · 盐哈希 ID

| 项 | 内容 |
|---|---|
| **目标** | claim_id / issue_id 稳定、不可反推、跨 run 一致 |
| **改** | `src/anon.py`（新）｜`pipeline.cluster`（生成 ID）｜`config/.salt`（新，进 git） |
| **接口** | `make_salt()` / `anon_id(seed, salt)` / `claim_seed(proj,file,anchor,category)` |
| **验收** | ① 同一 claim 在两次 run 里 ID 相同 ② 不同项目的同名文件 ID 不同 ③ 去掉盐后 ID 全变（证明依赖盐） |
| **工时** | 0.3 天 |
| **风险** | 盐丢失 = 题库作废 → 立刻备份到第二个位置 |

### T03 · 六类裁决标签 + 高严重度假报惩罚

| 项 | 内容 |
|---|---|
| **目标** | 支持 out_of_scope / trivial / uncertain / duplicate；虚报 P0/P1 额外扣分 |
| **改** | `pipeline.adjudicate`（合并规则）｜`pipeline.score`（`Fh` 项）｜`prompts/judge_v2.md`（六选一 + real_sev）｜`system.toml`（`high_sev_false_positive_penalty`） |
| **接口** | `adjudicate` 输出 `verdict ∈ 6 类`；`score` 增加 `fh_count` |
| **验收** | ① 六类各构造 2 条样例，裁决结果正确 ② 虚报 P0 的额外扣分按 `high_sev_false_positive_penalty = 2.0` 生效（率化分里表现为 `Fh × 4`） |
| **工时** | 1 天 |
| **风险** | 裁判不理解 out_of_scope，全判 rejected → 提示词里给三个例子 |

### T04 · 顺序双评

| 项 | 内容 |
|---|---|
| **目标** | 剔除位置偏差；不一致的条目标 unstable |
| **改** | `pipeline.make_packets`（生成正序/反序两版）｜`collect_votes`（配对）｜`adjudicate`（不一致处理）｜`system.toml`（`judge.order_swap`） |
| **接口** | 包文件名 `<claim_id>__a.md` / `<claim_id>__b.md` |
| **验收** | ① 同一包两版内容顺序确实相反 ② 两版结论不一致时 `verdict=uncertain` 且进队列 |
| **工时** | 0.5 天 |
| **风险** | 裁判调用量翻倍 → 用 `system.toml` 开关控制，首轮开，后续按需 |

### T05 · 埋点题库（inject）

| 项 | 内容 |
|---|---|
| **目标** | 在副本上埋已知 bug，让 recall 有真分母 |
| **改** | `src/inject.py`（新）｜`cli.py`（`inject plan/apply`）｜`bank/<proj>_golden.jsonl`（新） |
| **接口** | `plan(proj, n)` / `apply(proj, plan)` / `verify(proj)` / `golden(proj)` |
| **实现要点** | 四类埋点：① 删一行防御判断 ② `>=` 改 `>` ③ 漏 `await` ④ 异常分支返回 None |
| **验收** | ① 每类埋点都能被单测抓到 ② 埋点后单测从绿变红 ③ golden 里的 `file/line/severity` 与实际一致 |
| **工时** | 1.5 天 |
| **风险** | 埋的 bug 太明显，所有模型都能发现 → 区分度低；用"单测能抓到但人一眼看不出"的标准筛 |

### T06 · 并列判定 + 双分列

| 项 | 内容 |
|---|---|
| **目标** | 分差 <2 判并列；报告同时展示 raw_score 与 rate_score |
| **改** | `report._render_md`（并列标注、双列）｜`pipeline.score`（输出两套字段） |
| **验收** | ① 分差 1.7 的两个候选显示"第 1 名（并列）" ② rate_score 为 null 时显示"题库未成型" |
| **工时** | 0.5 天 |

**v0.2 合计：约 4.3 人天。**

## 三、v0.3 任务卡（让采集不痛苦）

### T07 · API 自动采集通道

| 项 | 内容 |
|---|---|
| **目标** | 对支持 API 的模型，跳过手工粘贴，自动记录耗时与 token |
| **改** | `src/collect_api.py`（新）｜`cli.py`（`api-run`）｜`candidates.toml`（`api_key_env` / `endpoint`） |
| **接口** | `run_api(candidate, task, prompt) -> raw_text, usage` |
| **验收** | ① 跑通一个模型 ② 时间/token 与手工记录误差 < 5% ③ 断网重试不重复计费 |
| **工时** | 2 天 |
| **风险** | API 结果 ≠ 产品结果（工具链不同）→ 只能作对照，不作主榜 |

### T08 · 精确 token 与耗时

| 项 | 内容 |
|---|---|
| **目标** | 从产品侧拿到可信的 token；拿不到就明确标 NA |
| **改** | `session_done`（增加 `token_source` 字段）｜报告（token 缺失率统计） |
| **验收** | 报告里能回答"4 个候选里哪几个的 token 是可信的" |
| **工时** | 0.5 天 |

**v0.3 合计：约 2.5 人天。可与 v0.2 并行。**

## 四、v1.0 任务卡（让历史不浪费）

### T09 · bank.py 核心

| 项 | 内容 |
|---|---|
| **目标** | 沉淀题库的读写、撞库、更新 |
| **改** | `src/bank.py`（新，约 400 行） |
| **接口** | `load_bank(proj)` / `match(claim, bank)` / `upsert(proj, issue)` / `recompute_found_by(proj)` |
| **实现要点** | 撞库三层（文件+行号 → 类别+标识符 → 裁判二选一），见 `06` 第五节 |
| **验收** | ① 构造 30 条历史 issue + 10 条新 claim，命中率与人工判断一致 ≥90% ② 行号整体 +3 后仍能命中 ③ 相邻两行两个不同 bug 不误合 |
| **工时** | 2.5 天 |
| **风险** | 行号漂移导致漏命中 → `hit_line_window` 可调；误合 → 提高标识符重叠阈值 |

### T10 · bank sync / hit 命令

| 项 | 内容 |
|---|---|
| **目标** | 把一次 run 的裁决结果沉淀；对新 run 做撞库并生成增量盲评卷 |
| **改** | `cli.py`（3 个命令）｜`pipeline`（调用 bank） |
| **接口** | `bank sync <run>` / `bank hit <run>` / `bank stat` |
| **验收** | ① r01 sync 后 bank 条数 = verdicts 中非 uncertain 条数 ② r02 hit 输出"命中 X 条、新增 Y 条" ③ 重跑 sync 幂等（不重复写） |
| **工时** | 1.5 天 |

### T11 · 率化分

| 项 | 内容 |
|---|---|
| **目标** | 实现 `rate_score`，含 Rw/P/C/F/Fh/T/U 七个量 |
| **改** | `pipeline.score`（新增分支）｜`system.toml`（`[rate_score]` 段）｜`report`（双列） |
| **验收** | ① 用 `07` 第四节的算例验证：A=46.9、B=22.4（±0.5） ② 题库未成型时输出 null 并给出原因 |
| **工时** | 1 天 |
| **风险** | 分母（bank 总权重）算错 → 单元测试固定一组数验证 |

### T12 · trend + fix_list

| 项 | 内容 |
|---|---|
| **目标** | 跨 run 趋势图；按项目输出可执行的待修清单 |
| **改** | `src/report.py`（`fix_list.md`）｜`cli.py`（`trend`） |
| **接口** | `fix_list`：按 `real_sev` 排序，每条含 `file:line`、`title`、`trigger`、证据级别 |
| **验收** | ① fix_list 能直接当待办用（不漏行号、不重复） ② trend 只在四个版本号一致时画图 |
| **工时** | 1 天 |

**v1.0 合计：约 6 人天。**

## 五、优先级矩阵

按"价值 ÷ 成本"排序，而不是按版本顺序：

| 任务 | 价值 | 成本 | 性价比 | 建议顺序 |
|---|---|---|---|---|
| T01 evidence 校验 | 高（干掉幻觉） | 0.5d | ★★★★★ | 1 |
| T06 并列 + 双列 | 高（防误读排名） | 0.5d | ★★★★★ | 2 |
| T03 六类标签 | 高（表达力） | 1d | ★★★★☆ | 3 |
| T10 bank 命令 | 高（可复用入口） | 1.5d | ★★★★☆ | 4 |
| T09 bank 核心 | 高 | 2.5d | ★★★☆☆ | 5 |
| T11 率化分 | 中高（跨 run 可比） | 1d | ★★★☆☆ | 6 |
| T02 盐哈希 | 中（稳定性） | 0.3d | ★★★★☆ | 7 |
| T12 trend/fix_list | 中（可用性） | 1d | ★★★☆☆ | 8 |
| T05 埋点 | 高（recall 分母） | 1.5d | ★★★☆☆ | 9 |
| T04 顺序双评 | 中（抗位置偏差） | 0.5d | ★★★☆☆ | 10 |
| T08 精确 token | 低 | 0.5d | ★★☆☆☆ | 11 |
| T07 API 采集 | 中（省人力） | 2d | ★★☆☆☆ | 12 |

**先做 T01 + T06**：两天不到，就能让第一轮结果"可信且不被误读"。这两件是"最小可信产品"。

## 六、里程碑

| 里程碑 | 包含 | 产出 | 预计 |
|---|---|---|---|
| **M1 最小可信** | T01 + T06 | 能出一份不会误导读者的报告 | 1 天 |
| **M2 首轮实测** | M1 + 采集 10 项目 × 4 候选 | 第一份真实榜单 + 首轮 bank | 5 天（含采集） |
| **M3 可复用** | T02 + T03 + T09 + T10 | 第 5 个模型不用重跑裁决 | +4 天 |
| **M4 跨 run 可比** | T11 + T12 | 趋势 + 率化分 | +2 天 |
| **M5 硬化** | T04 + T05 + T08 | 抗位置偏差 + recall 真分母 | +3 天 |
| **M6 自动化** | T07 | API 通道 | +2 天 |

**建议节奏**：先 M1（1 天）→ 立刻跑 M2（5 天）→ 用真实数据决定 M3 怎么做。不要在没有数据的情况下把 M3–M6 全部实现。

理由：`bank` 的撞库阈值（±15 行、标识符重叠 0.5）必须用真实数据校准。空想的参数一定不准。

## 七、每版的验收清单

### v0.2 验收

- [ ] 10 条假 evidence 全部被拒
- [ ] 六类裁决标签各有一条样例通过
- [ ] 虚报 P0 的额外扣分按 `high_sev_false_positive_penalty` 生效（绝对分 2.0/条；率化分 `Fh×4`）
- [ ] 顺序双评不一致时进 uncertain
- [ ] 分差 1.7 显示并列
- [ ] rate_score 为 null 时报告有提示
- [ ] `demo` 仍能一键跑通（不回归）

### v1.0 验收

- [ ] r01 sync 后 bank 条数正确
- [ ] 重复 sync 幂等
- [ ] r02 撞库命中率 ≥ 65%
- [ ] 新模型命中后，老模型独到加成正确降级
- [ ] rate_score 与手算一致
- [ ] trend 拒绝混合版本号的 run
- [ ] fix_list 可直接当待办

### 每版都必查的三个回归

1. `python src/cli.py demo` 能跑通（端到端不退化）
2. 旧 run 的 `score` 结果与改动前一致（除非刻意改公式）
3. `runs/<run>/raw/` 未被修改（`git status` 干净）

## 八、一个人做的时间账

| 阶段 | 人天 | 说明 |
|---|---|---|
| v0.2（T01–T06） | 4.3 | 集中做 5 天够 |
| 首轮采集 | 4 | 4 个候选 × 每天 1 个 |
| v1.0（T09–T12） | 6 | 撞库需要调参，留缓冲 |
| v0.3（T07–T08） | 2.5 | 可选 |
| **合计** | **约 17 人天** | 分散在 4–6 周 |

如果只有周末做，大约两个月能到 v1.0 可用状态。
