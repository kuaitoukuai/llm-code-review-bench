# 08 历史复用与版本

> 需求 R1 的原话是"以后想增加新大模型测试——git 版本存档，曾经测评数据、评分依然可用——沉淀"。
> 这一篇把"依然可用"拆成四个层次，逐个给出实现。

---

## 一、复用的四个层次

很多人以为"可复用"就是"数据别删"。实际上有四个层次，缺一层就断。

| 层次 | 复用什么 | 没有它会怎样 | 实现 |
|---|---|---|---|
| **L1 快照复用** | 同一份代码 | 新模型面对的是改过的代码，分数不可比 | `eval_repos/` 只读副本 + `git tag` |
| **L2 答案复用** | 已裁决的真伪判断 | 每次都要重判 200 条，成本不可承受 | `bank/<proj>_bank.jsonl` |
| **L3 规则复用** | 评分公式与提示词 | 换个参数就要重跑模型 | 双版本号 + `score` 只读裁决层 |
| **L4 结论复用** | 历史排名与趋势 | 无法回答"这个模型比半年前强多少" | `score_at_run` 快照 + `trend` 命令 |

**四层是递进的**：没有 L1，L2 的答案会对不上代码；没有 L2，L3 的重算仍然要重新裁决；没有 L3，L4 的趋势没有可比口径。

## 二、L1：快照冻结

### 2.1 问题

你会用一审结果直接去修项目的真 bug。修完之后，代码变了。两个月后测新模型，它面对的是"已修复版"，而老模型面对的是"有 bug 版"——**卷子不一样了**。

### 2.2 两种冻法

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. git tag** | 在项目里打 `eval-v1` 标签 | 零额外存储、可 diff | 依赖项目有 git；打 tag 后不能 rebase |
| **B. 只读副本** | 把 `target_dirs` 复制到 `eval_repos/<proj>/` | 独立于项目 git，绝对稳定 | 多一份存储（几十 MB） |
| **C. 两者都做** | tag 记录血统，副本保证可用 | 最稳 | 要维护两处 |

**推荐 C**，但优先级是：**先做 B**（因为绝对稳定），有余力再做 A（为了可追溯）。

### 2.3 副本的构造规则

```python
# 伪代码
def freeze(proj):
    src = Path(proj.path)
    dst = ROOT / "eval_repos" / proj.id
    for d in proj.target_dirs:
        copy_tree(
            src / d, dst / d,
            exclude=["node_modules", "dist", "build", ".next",
                     "*.min.js", "*.map", "*.log", "__pycache__", ".venv"]
        )
    # 记录清单
    write_jsonl(dst / "_manifest.jsonl", [
        {"path": p, "sha1": sha1(p), "lines": count_lines(p)}
        for p in walk(dst)
    ])
    # 置只读（Windows: attrib +R；Linux: chmod -R a-w）
    make_readonly(dst)
```

三个细节：

1. **排除规则要写死在代码里**，不能靠人工记。漏一个 `node_modules`，副本从 20 MB 变 800 MB。
2. **必须生成 `_manifest.jsonl`**，记录每个文件的 sha1。后续"代码是否漂移"靠它判断。
3. **必须置只读**。不然某次误操作改了副本，所有历史分数作废。

### 2.4 快照与 tasks 的关系

```
eval_repos/<proj>/           ← 只读源码副本（人看、模型看都可以）
tasks/<task>/files.jsonl     ← 从副本里抽出的、真正喂给模型的那部分（含 content）
```

两者内容一致，但用途不同：副本用于"跑测试/复现"，`files.jsonl` 用于"拼提示词"。

## 三、L2：答案复用（bank）

已在 `06` 详述，这里只强调三个与版本相关的点：

| 点 | 规则 |
|---|---|
| `found_by` 会增长 | 每次新模型命中，追加；`bank_version += 1` |
| `verdict` 可被推翻 | 平反要保留原裁决记录（用于统计裁判准确率） |
| `issue_id` 不可变 | 生成算法一旦上线就冻结 |

## 四、L3：双版本号

### 4.1 四个版本号（同 `03` 第六节）

| 版本 | 管什么 | 升版触发 |
|---|---|---|
| `dataset_vN` | 项目集合 + 快照 + golden | 增删项目、更新快照、改埋点 |
| `rubric_vN` | 提示词 + 字段 + 校验 | 改提示词、加字段、改上限 |
| `bank_vN` | 沉淀题库状态 | 每次 sync / 平反 / 合并 |
| `scoring_vN` | 评分公式与权重 | 改权重、改公式 |

### 4.2 重算矩阵

这是本篇最重要的一张表。五种变更场景，分别要重跑什么：

| 变更 | 要重跑 | 不用重跑 | 历史分数 |
|---|---|---|---|
| **只改评分权重**（scoring+1） | `score` | normalize / cluster / 裁决 / 采集 | 重算后变化，但**原始数据不动** |
| **只改提示词**（rubric+1） | 采集 → normalize → 之后全部 | — | 不可比，必须标注 |
| **只加新模型**（bank 不变） | 采集新模型 → normalize → 撞库 → 增量盲评 → score | 老模型的采集与裁决 | 老模型分数**不变**（除非新模型发现新问题） |
| **新模型发现新问题**（bank+1） | 全量 `score_now` 重算 | 无需重新采集 | 老模型 recall 下降，独到加成降级 |
| **代码大改**（dataset+1） | 全部 | — | 建立新基线，旧分数归档 |

### 4.3 一个具体的"只改权重"演练

```
1. 改 config/system.toml：P0 从 8 改成 10
2. python src/cli.py score r01
3. 输出：scores.json 里 scoring_version 变成 scoring_v3
4. 报告顶部自动加一行："本报告使用 scoring_v3，与历史 scoring_v2 不可直接比较"
```

第 4 步是自动的，不能靠人记。实现方式：`report` 读 `run.json` 的 `scoring_version`，与当前 `system.toml` 比对，不一致就加警告。

## 五、分数漂移的可解释性

同一个模型，同一个项目，两次跑出不同分数——必须能在 3 分钟内解释清楚"为什么变了"。

### 5.1 六种漂移来源

| # | 来源 | 表现 | 怎么查 |
|---|---|---|---|
| 1 | 模型随机性 | 同配置两次差 <10% | `scores.jsonl` 逐条对比 |
| 2 | 题库更新（bank+1） | 老模型 recall 下降，新模型 recall 上升 | `bank_version` 变化 |
| 3 | 独到加成降级 | 某条从 2.0 变 1.3 | `bank` 里看 `found_by` 长度 |
| 4 | 评分规则变更 | 全体分数整体平移 | `scoring_version` |
| 5 | 代码快照变更 | 题目不同了 | `dataset_version` |
| 6 | 采集故障 | 某项目 `status=timeout` | `run_logs.jsonl` |

### 5.2 报告里的"变更说明"块

每次生成报告，自动附一段：

```markdown
## 本次分数与上次的差异

对比基准：r01（2026-11-14）

| 项 | r01 | r03 | 变化 | 原因 |
|---|---|---|---|---|
| dataset | v1 | v1 | — | 同一批快照 |
| rubric | v2 | v2 | — | 同一套提示词 |
| bank | 1 | 3 | +2 | 新增 12 条 issue，2 条独到降级 |
| scoring | v2 | v2 | — | 公式未变 |
| claude-sonnet-5.5 | 46.9 | 44.1 | −2.8 | 独到降级 1 条（−3.0），新增命中 1 条（+0.2） |
```

这张表让"分数为什么变"变成可查的事实，而不是玄学。

## 六、L4：趋势

```bash
python src/cli.py trend --proj t05-shadow --metric rate_score
```

输出：

```
t05-shadow   rate_score 趋势（dataset_v1 / scoring_v2）
  r01  2026-11-14  claude 46.9  kimi 45.2  glm 38.1
  r02  2026-11-21  claude 47.1  kimi 45.0  glm 39.4   ← bank+1
  r03  2026-12-05  claude 44.1  kimi 46.8  glm 40.2   ← 新模型发现 2 条新问题
```

趋势图的价值不在"谁涨了"，在**"涨的原因"**。三种典型形态：

| 形态 | 含义 |
|---|---|
| 全体同步上升 | 题库在变简单（bug 被修了但没 deprecate） |
| 某个模型单独上升 | 它真的进步了，或它的风格更适应这批题 |
| 全体下降 | 题库变难（新增了难题），或评分变严 |

**没有变更说明的趋势图是没有意义的。** 所以 `trend` 必须读 `run.json` 的四个版本号，版本不一致的 run 不画在同一张图上。

## 七、数据保留策略

### 7.1 体积估算

| 项 | 单次 run | 一年（20 run） |
|---|---|---|
| raw（40 份回复 × 30 KB） | 1.2 MB | 24 MB |
| normalized + claims | 0.8 MB | 16 MB |
| judgments（含 packets） | 1.5 MB | 30 MB |
| reports | 0.3 MB | 6 MB |
| **合计** | **约 4 MB** | **约 80 MB** |

80 MB 完全可以全部进 git。**不要只留 report 删掉 raw**——raw 是唯一不可再生的数据。

### 7.2 git 策略

```gitignore
# 不进 git
runs/*/raw/*/*/*.md.tmp
__pycache__/
*.pyc
config/.salt          ← 不，这个要进！见下方

# 进 git
config/  prompts/  src/  tasks/  bank/  runs/  reports/  eval_repos/（若 <50MB）
```

> ⚠️ `config/.salt` 必须进 git 且备份。它丢了，所有 `issue_id` 失效，题库作废。
> 它不是密钥（不用于认证），只是一个稳定哈希盐，泄漏无安全风险，丢失才有风险。

### 7.3 归档

每季度：

```bash
tar -czf archive/2026Q4_runs.tar.gz runs/2026-10-* runs/2026-11-*
```

归档后可以删 `runs/` 里的旧目录，但 `bank/` 必须保留（它是浓缩后的资产）。

## 八、迁移：从 v0.1 的 runs 到 v1.0 的 bank

现有 `runs/demo-001/` 是 demo 数据，不用迁移。但如果有真实 run，迁移步骤：

```
1. 确认 verdicts.jsonl 存在且非空
2. 逐条算 issue_id（用 05 的算法）
3. 写入 bank/<proj>_bank.jsonl，bank_version=1
4. 标 first_seen = 该 run_id
5. found_by 从 origin.jsonl 反查
6. 校验：bank 条数 == verdicts 条数（去掉 uncertain/duplicate）
7. 用 bank 重算一次 score_now，与原始 score 对比
   差异应仅来自"独到加成降级"（因为 found_by 现在有完整信息）
```

第 7 步的对比很重要——如果差异很大，说明迁移有 bug，或者原始 run 的 found_by 记录不全。

## 九、可复用的边界

诚实一点：这套设计解决不了两种情况。

| 场景 | 为什么解决不了 |
|---|---|
| **项目重构后** | 代码结构变了，`issue_id` 全变，等于换了一套卷子。只能升 `dataset_vN` 重建。 |
| **模型大幅升级后** | 老模型的分数是"旧版本模型"的成绩，与新版不可比。要保留 `model_version` 字段，且报告里不能把 GPT-5.5 和 GPT-6 放在同一张榜。 |

第二条尤其容易犯：看到一个模型分数涨了 3 分，以为它进步了，其实是版本换了。所以 `candidates.toml` 里 `id` 必须带版本号（`kimi/kimi-k2.5` 而不是 `kimi`）。
