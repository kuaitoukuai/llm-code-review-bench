# 10 风险与局限

> 一份诚实的设计文档，价值在于它写清楚了"什么时候不能用"。
> 这一篇列十二个失灵场景、四类作弊路径、一条结论可信度分级。

---

## 一、先算一个数：裁判到底有多准

整套系统的地基是"交叉验证能逼近真相"。这个"逼近"有多近，取决于一个数：**单模型对"这条 bug 是否成立"的判断正确率 p**。

没有人测过代码审查场景下的 p。但可以从两个间接数据估：

| 参考 | 数据 | 推论 |
|---|---|---|
| LLM 裁判与人类专家的一致率（专业领域） | 60%–68% | p 大约在 0.6–0.7 |
| 假阳性审计：被判为假的条目里约 1/3 其实有用 | precision 被低估 | 实际 p 可能略高于表面值 |

按 p = 0.65 算，三票多数后 ≈ 0.72，五票多数后 ≈ 0.76。**这就是这套系统能达到的上限区间：七成多一点。**

所以：

- 任何"这条 bug 一定存在"的断言，都要降级成"三个独立裁判里两个认为是真的"
- 任何"某模型比某模型强 X%"的结论，在 X < 10 时都不要说

### 1.1 p 在什么情况下会掉到 0.5 以下

| 情况 | 为什么 | 表现 |
|---|---|---|
| 领域极专（如并发、加密、协议） | 模型缺乏足够的领域语料 | 裁判自己都看不懂，随机猜 |
| 代码片段被截断 | 看不到上游校验，误判"没判空" | 系统性偏向"报有问题" |
| 问题表述含糊 | "这里可能有性能问题" | 无法判定真假 |
| 代码规范与训练语料差异大 | 少见写法被当成错误 | 系统性误报 |

**对策**：遇到这四类条目，直接进人工队列，不要浪费裁判票。

## 二、十二个失灵场景

| # | 场景 | 后果 | 现有缓解 | 残余风险 |
|---|---|---|---|---|
| 1 | **全体模型都漏掉的 bug** | recall 虚高，看起来"都很强" | 埋点题库（T05） | 高：埋点只能覆盖已知类型 |
| 2 | **同族模型犯同一个错** | 共识推断把它当真相 | vendor 去重 | 中：只能按厂商分，同厂不同代仍相关 |
| 3 | **裁判自己看不懂** | 判成 uncertain 或乱判 | 进人工队列 | 高：人工也未必看得懂 |
| 4 | **聚类误合并** | 两个 bug 算一个，所有候选都少拿分 | 标识符交集规则 | 中：同名函数仍会误合 |
| 5 | **聚类误拆分** | 一个 bug 算两个，报得多的占便宜 | 无 | 中：靠人工 merge |
| 6 | **产品与模型未分离** | 分不清是模型强还是工具强 | 报告标注 | 高：设计如此，不可解 |
| 7 | **单次噪声** | 10% 内的差距无意义 | 并列判定 + repeat | 低：已用阈值处理 |
| 8 | **裁判圈子闭环** | 作答与裁判是同一批模型 | 引入第 5 个 vendor | 中：整个行业就这么几个模型 |
| 9 | **题库偏见** | 题目都是你的代码，某类风格占优 | 多项目混合 | 中：自建题库的固有代价 |
| 10 | **代码漂移** | 修完 bug 后题面变了 | 快照冻结 | 低：已有 eval_repos |
| 11 | **采集故障被当成能力差** | 超时的候选分数低 | `status` 打标 | 低：报告里单列 |
| 12 | **模型知道自己在考试** | 过度报告、刻意表现 | 提示词不透露"评测" | 中：无法完全隐藏 |

### 2.1 最危险的第 1 条，展开说

"全体模型都没发现的 bug"是这套系统的结构性盲区。它的数学后果：

```
真实 bug 总数 = 已知（bank）+ 未知
报告里的 recall = 命中 / 已知
真实 recall     = 命中 / (已知 + 未知)
```

只要"未知"不为零，报告里的 recall 就偏高。偏高多少，取决于你的代码里还有多少没被发现的问题——**这个数永远不知道**。

所以报告里必须写"**当前已知问题加权召回率**"，不能写"召回率"。这不是文字游戏，是防止自己骗自己。

三种补漏方式（按性价比排序）：

| 方式 | 成本 | 效果 |
|---|---|---|
| 埋点（inject） | 中（1.5 天开发 + 每项目 30 分钟） | 直接给出确定的未知名单，最有效 |
| 真实 bug 回流（线上出问题后补进 bank） | 零（等它发生） | 慢，但 100% 真实 |
| 定期人工审计（换提示词重跑） | 高（半天/项目） | 能发现新类型，但不可持续 |

## 三、四类作弊路径

### 3.1 模型侧

| 路径 | 表现 | 防法 |
|---|---|---|
| **凑数** | 报满 12 条，蒙中 2 条 | 误报扣分 + 上限 8 条 + `min_findings` 兜底 |
| **虚报严重度** | 把 P2 说成 P0，博取高权重 | `Fh` 额外扣 4 倍 |
| **写长文** | 用"综上所述""值得关注"填充 | 字段硬上限 + 无总结字段 |
| **抄同批答案** | 如果能看到别人的报告 | 一条一包，互相不可见 |
| **识别自己** | 认出自己的文风，给自己高分 | 双盲 + 可选作者混淆 |
| **背题** | 训练数据里见过这段代码 | 私有代码 + 近期修改优先 |

### 3.2 人侧（你自己）

| 路径 | 表现 | 防法 |
|---|---|---|
| **确认偏误** | 看到"我喜欢的模型"报了，就觉得对 | 人工队列里不显示来源（默认已是这样） |
| **疲劳** | 判到第 20 条时草率 | 一次不超过 25 条；分批 |
| **改规则救场** | 结果不满意就调权重 | 改权重必须重算全部历史，且记 `scoring_version` |

最后一条最隐蔽。调参本身没错，但"只调这一次、不重算历史"就是作弊。所以 `score` 必须是无状态的纯函数：同样的输入永远给同样的输出。

### 3.3 数据侧

| 路径 | 表现 | 防法 |
|---|---|---|
| **挑题目** | 只留"某模型表现好"的项目 | 题库一旦冻结就不许改（改则升 `dataset_vN`） |
| **挑重复次数** | 跑三次取最高分 | 固定 repeat 次数，取中位数不取最大 |
| **删失败样本** | 超时的候选直接不列 | `status=timeout` 也要进表，标灰 |

### 3.4 系统侧

| 路径 | 表现 | 防法 |
|---|---|---|
| **裁判泄漏** | 包里不小心带了 candidate | 单元测试：断言包文本不含候选名 |
| **顺序泄漏** | 按候选顺序生成包，裁判能推断 | 包顺序随机化 |
| **ID 反推** | 顺序 ID 暴露提交顺序 | 盐哈希（T02） |

## 四、数据与合规

私有代码不出本机，是这套系统的底线。但实际执行时有三处会漏：

| 漏点 | 风险 | 处理 |
|---|---|---|
| **粘贴到云端产品** | 代码进入对方服务器，可能被用于训练 | 只选明确承诺"不使用用户数据训练"的产品；敏感项目不上榜 |
| **裁判包发给第三方 API** | 代码片段外泄 | 裁判用本地模型，或只发"最小必要片段"（`context_lines` 控制） |
| **报告分享** | 报告里有完整代码片段和文件路径 | 分享前跑 `report --redact`（脱敏：路径打码、代码片段截断） |

### 4.1 什么项目不能进题库

- 含真实密钥、证书、Token 的（哪怕在 `.env` 里）
- 客户交付物且有保密条款的
- 含个人隐私数据的（用户表结构、日志样例）

`task` 命令应该在冻结前扫一遍：正则匹配 `AKIA[0-9A-Z]{16}`、`-----BEGIN.*PRIVATE KEY-----`、`sk-[A-Za-z0-9]{20,}` 等模式，命中就拒绝冻结并报出行号。

这个检查现在没有，是 v0.2 应该加的一个 20 行的小功能。

## 五、结论可信度分级

报告里的每条结论，都应该带一个等级。三级就够：

| 等级 | 条件 | 能怎么用 |
|---|---|---|
| **A 可直接行动** | 证据级别 E1（执行复现）或 E2（人工确认），且 `real_sev ∈ {P0,P1}` | 直接照着修 |
| **B 可参考** | E3（≥2 裁判一致）或 E2 但低严重度 | 看一眼，自行判断 |
| **C 仅供观察** | E4（共识推断）或 `uncertain` | 不当结论用，只当"值得看一眼" |

报告结构建议：

```
## A 级（12 条，建议本周修）
## B 级（23 条，有空看）
## C 级（41 条，仅供参考）
## 未决（8 条，需要你裁决）
```

按等级分节，比按项目分节更实用——因为你修 bug 是按严重度排优先级，不是按项目。

## 六、什么时候不该用这套系统

四条红线：

| 场景 | 为什么不适合 | 该用什么 |
|---|---|---|
| **想决定"买哪个 AI 编程工具"** | 这套系统测的是"找 bug"，不是"写代码/补全/重构" | 直接用一周，记录实际节省时间 |
| **代码量 < 500 行** | 样本太少，一条误报就能翻转排名 | 人工 code review |
| **需要合规审计结论** | 交叉验证是"逼近"不是"证明"，不能作为审计证据 | 专业安全审计 + SAST 工具 |
| **团队要落地代码门禁** | 每次 2 小时 + 人工复核，太慢 | ESLint / SonarQube / 单测覆盖率门禁 |

这套系统的定位很窄：**在你自己的代码上，用较低成本回答"这几个模型哪个更会找我这类 bug"。** 超出这个范围，它就不划算了。

## 七、三条元风险

比技术风险更值得警惕的，是这三条：

### 7.1 把工具当结论

跑完一轮，看到"claude 46.9，kimi 45.2"，就下结论"claude 更强"。实际上 1.7 分的差距在噪声范围内（`07` 第七节）。

**对策**：报告第一页就写"分差 <2 判并列"，且并列的两个都标"第 1 名"。

### 7.2 为了分数优化系统

发现某个模型总是报 P3，就把 P3 权重调到 0，让它分数掉下来——这叫"对着答案调参"。

**对策**：权重调整必须一次调完、全部重算、记录版本。不许"只调这一次"。

### 7.3 系统越复杂，越没人用

12 张任务卡、4 个版本号、6 类标签——这套东西的复杂度已经接近一个内部工具的上限。如果维护成本超过"每季度跑一次"的频率，它就会荒废。

**对策**：`demo` 必须永远能一键跑通。它是这套系统的"健康检查"——如果 `demo` 挂了，说明有人在改代码时忘了兼容，这时应该停下来修，而不是继续加功能。

---

## 八、一句话总结

**这套系统的可信度上限，由"裁判有多准"决定，不由"公式有多精巧"决定。**

所以所有的工程投入，都应该优先投在"增加证据强度"（执行复现、人工抽检、埋点），而不是"优化评分公式"。
