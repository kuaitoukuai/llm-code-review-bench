# 06 裁决与共识题库

> 这一篇是"可复用"的全部技术含量所在。
> 核心问题只有一个：**一条 bug 的真伪判断，怎么变成可以反复使用的资产？**

---

## 一、四级证据链

不是所有"确认"都同样硬。系统按证据强度分四级，报告里必须标明每一条的级别。

| 级别 | 通道 | 判定方式 | 单条成本 | 强度 |
|---|---|---|---|---|
| **E1** | 执行复现 | 模型自己写的测试跑红了 | 0（本地跑） | **最硬**：跑得出来就是真的 |
| **E2** | 人工 | 你看过并判定 | ~2 分钟 | 硬：人类判断，但会疲劳/主观 |
| **E3** | 裁判票 | 跨族裁判 ≥2 票一致 | 几分钱 | 中：与人类一致率 60–68% |
| **E4** | 共识推断 | 无票，但 ≥2 家（不同 vendor）提出 | 0 | 弱：可能是同一个幻觉模式 |

### 1.1 为什么执行复现排在人工前面

人工判断会错——尤其是"这个并发问题到底会不会发生"这类。而"跑红的测试"不会错，只要测试本身是对的。

但执行复现有前提：模型得写出一个能跑的最小测试。这就是 `review_v2` 存在的意义。它的代价是：

- 模型要花时间写测试（采集成时长 +30%）
- 测试本身可能是错的（测试写错了，"跑红"也是假的）
- 执行模型生成的代码有安全风险（需要独立目录 + 超时 + 显式授权）

`config/system.toml` 里已有 `[execution]` 段：`timeout_seconds = 15`、`max_test_chars = 12000`。**执行前必须人工审查一遍代码**，这不是形式主义——那是别人（模型）写的代码，在你的机器上跑。

### 1.2 证据级别怎么进报告

每条结论后面标一个字母：

```
K-7Q2M  P1  concurrency  apps/api/src/orders/service.ts:142  [E1]
  库存扣减与判断之间没有原子性保护，并发下单会超卖
  证据：exec/orders_test.py 跑红（expected 1, got -1）
```

读者一眼能看出这条有多可信。比混成一个总分诚实得多。

## 二、六类标签的落地映射

`03` 定义了六类标签，这里说清楚它们怎么和四级证据链配合。

| 标签 | 典型来源 | 能否进 bank | 计分 |
|---|---|---|---|
| `confirmed` | E1 / E2 / E3（≥2 票） | ✅ 进，`verdict=confirmed` | 命中，按 `real_sev` 加权 |
| `rejected` | E2 / E3（≥2 票） | ✅ 进，`verdict=rejected` | 误报扣分 |
| `out_of_scope` | E2 / E3 | ✅ 进，但标 `status=deprecated` | 不计命中也不计误报 |
| `trivial` | E2 | ✅ 进 | 默认 0 分（可配 0.5） |
| `uncertain` | 票数不足 / 双评不一致 | ❌ 不进（除非转人工） | 不奖不罚，进队列 |
| `duplicate` | 聚类阶段 | 合并到主条目 | 不单独计分 |

### 2.1 `out_of_scope` 为什么重要

实际跑下来会发现，模型报的问题里有相当一部分是"真问题，但不是这个项目的问题"：

- 依赖库的已知漏洞（`npm audit` 就能查）
- 框架层面的设计问题（"建议改用 X 架构"）
- 测试代码里的问题（不在审查范围）

如果这些都算误报，会系统性低估模型的 precision。所以给一条中立通道：**记录，但不算账**。

## 三、裁决合并的完整规则

```
输入：一条 cluster，N 张裁判票，可能有人工裁决，可能有执行结果

1. 若有人工裁决（human.jsonl）
   → 直接采纳，confidence = human
   → 结束

2. 若有执行结果（exec/*.json）
   → status = red   → confirmed，real_sev 取提交者声称（测试证明了存在）
   → status = green → rejected（测试跑绿说明问题不成立）
   → status = error → 忽略，降级到第 3 步

3. 若有裁判票
   a. 先剔重：同一 judge 的多票只算一票
   b. 顺序双评不一致的 → uncertain
   c. ≥2 票 confirmed 且 0 票 rejected → confirmed
   d. ≥2 票 rejected → rejected
   e. 1:1 → uncertain（进仲裁）
   f. 全 uncertain → uncertain
   g. real_sev 取所有 confirmed 票的中位数

4. 无票，走共识推断
   support_vendor >= 2 且 support_count >= 2 → inferred_confirmed
   否则 → pending（进人工队列，若 real_sev ∈ {P0,P1}）
```

### 3.1 仲裁怎么做

`1:1` 的情况会累积。处理顺序：

1. 加第三票（如果还没到 `panel_size=3`）
2. 三票仍分歧 → 人工
3. 人工也没空 → 留在 `uncertain`，报告里单列一节"未决条目"

**不要为了凑数把 `uncertain` 强行判成 confirmed 或 rejected。** 不确定性是真实存在的，掩盖它只会让排名看起来更确定，实际上更不可信。

## 四、沉淀题库（issue_bank）

### 4.1 它是"跨 run 的真相账本"

`runs/<run>/judgments/verdicts.jsonl` 是"这次评测的判断"。
`bank/<proj>_bank.jsonl` 是"这个项目到目前为止，所有被判断过的问题"。

区别：

| | verdicts.jsonl | bank.jsonl |
|---|---|---|
| 范围 | 单次 run | 跨 run 累积 |
| 内容 | 本次提出的 claim 的裁决 | 所有历史 claim 的裁决 + 合并关系 + 发现者 |
| 可变性 | 可重算覆盖 | 只追加，状态可改（平反/合并） |
| 用途 | 算这次的分 | 撞库、算历史分、算独到归属 |

### 4.2 结构（与 `03` 第四节一致）

```jsonl
{"issue_id":"K-7Q2M","proj":"t05-shadow","file":"apps/api/src/orders/service.ts",
 "line":142,"line_end":150,"category":"concurrency","verdict":"confirmed","real_sev":"P1",
 "found_by":["kimi/kimi-k2.5"],"first_seen":"r01","last_seen":"r01","bank_version":1,
 "status":"active","merged_from":[],"evidence_digest":"sha1:8f2c...","note":"库存超卖"}
```

### 4.3 `found_by` 的三个状态

| 状态 | 含义 | 加成 |
|---|---|---|
| 1 个发现者，且是 confirmed P0/P1 | 独到发现 | ×2.0 |
| 2 个发现者 | 稀有发现 | ×1.3 |
| ≥3 个发现者 | 常见发现 | ×1.0 |

这就是"独到加成动态归属"：一条 bug 在被第二个模型也发现之后，加成自动从 2.0 降到 1.3，**所有历史模型的分数都要重算**。

### 4.4 为什么要"降级"而不是"保持不变"

如果保持 2.0，会出现一个荒谬的场景：模型 A 在 r01 独享一条 bug 得 2.0 倍分；模型 B 在 r03 也发现了同一条，得 1.0 倍分。同一个 bug，两个人付出同样的洞察，得分差一倍——只因为谁先跑。

降级机制让"独到"回归它的本意：**在已知的全体候选里，只有你发现了**。这个"全体"应该随时间扩大。

代价是历史分数会变。所以 `08` 里设计了"当时分 / 当前分"双轨。

## 五、撞库算法

新模型跑完，拿它的 claim 去 `bank` 里查"这条是不是已经被判断过"。命中就不需要重新裁决。

### 5.1 三层匹配

```
输入：新 claim（file, line, line_end, category, title, evidence）
      bank（该项目的所有 issue）

第 1 层：文件 + 行号区间
  候选 = bank 中 file 相同（归一化后）且
         [line-15, line_end+15] 与 issue 的 [line, line_end] 有交集
  若候选为空 → 未命中，进增量盲评
  若候选唯一 → 进第 2 层校验
  若候选多个 → 进第 2 层排序

第 2 层：类别 + 标识符
  优先选 category 相同的
  若仍多个，比较 evidence 里的标识符集合（函数名/变量名）重叠度
  重叠度最高且 > 0.5 → 命中
  否则 → 进第 3 层

第 3 层：裁判二选一（只对存疑的少数）
  把"新 claim"和"bank 里最像的那条"一起给裁判：
  "这两条说的是不是同一个问题？只回答 yes 或 no"
  成本 < 200 token
```

### 5.2 为什么第 1 层用 ±15 行

行号漂移的经验值：改一个函数里的几行，下游偏移通常在 10 行以内；重构一个文件，偏移会到几十行，那种情况下本来就该重新裁决。

±15 行是"能容忍小改动，但不会把相邻两个不同 bug 混为一谈"的折中。这个值在 `config/system.toml` 里可调。

### 5.3 撞库的三个结果

| 结果 | 处理 | 计分 |
|---|---|---|
| **命中 confirmed** | 把当前候选加入 `found_by`，重算独到加成 | 直接得分，不用裁决 |
| **命中 rejected** | 记为误报 | 直接扣分 |
| **未命中** | 生成"增量盲评卷"，交裁判或人工 | 裁决后写入 bank |

### 5.4 命中率的意义

`hit_rate = 命中数 / 总提报数`

| 命中率 | 含义 | 行动 |
|---|---|---|
| > 85% | 题库成熟，新模型几乎没有新发现 | 正常，说明这批模型同质 |
| 65%–85% | 健康 | 增量盲评量可控 |
| 40%–65% | 题库偏薄，或新模型确实更强 | 值得关注，看未命中的是什么 |
| < 40% | 两种情况：新模型发现了大量新问题（好事），或它在乱报（坏事） | 必须人工抽样 10 条判断 |

**注意**：命中率低不一定是坏事。如果新模型真的发现了 20 条老模型都没发现的问题，那是这套系统最有价值的时刻。

## 六、增量盲评流程

新模型 `Model_New` 跑完 10 个项目后：

```
1. 逐条撞库
   ├─ 命中 → 更新 found_by，结束
   └─ 未命中 → 进待评队列

2. 待评队列去重（防止它自己重复报同一条）

3. 生成《增量盲评卷》
   ├─ 每条一个包（与常规裁判包同格式）
   └─ 只发给非参赛裁判

4. 回收裁决
   ├─ confirmed → 写入 bank（新 issue）
   └─ rejected  → 写入 bank（verdict=rejected）

5. 重算
   ├─ bank_version += 1
   ├─ 所有历史 run 的 score_now 重算
   └─ 输出"本次新增问题"清单
```

### 6.1 增量盲评的量级

首轮建库后，第 5 个模型的典型情况：

| 项 | 数量 |
|---|---|
| 总提报 | 约 200 条 |
| 撞库命中 | 140–170 条（70–85%） |
| 未命中 | 30–60 条 |
| 去重后 | 20–40 条 |
| 需要裁判 | 20–40 条 × 3 票 = 60–120 次调用 |

**这就是"可复用"的全部价值**：从"200 条全要裁决"降到"30 条要裁决"，省 85% 的成本。

### 6.2 一个必须处理的边界：新模型报的是"老模型的盲区"

如果新模型报的 20 条全部 confirmed，说明老模型的 recall 被系统性低估了。这时候要做两件事：

1. 把这 20 条写进 bank，标 `first_seen = r05`
2. **给所有历史模型记"未发现"**，然后重算 recall

这会拉低所有历史模型的召回率。这是正确的——他们确实漏了。但要在报告里注明"因新增问题导致历史分数下调"，否则看起来像系统不稳定。

## 七、题库维护

bank 不是只写不读的日志，它需要维护。四种操作：

### 7.1 合并（merge）

**场景**：同一个 bug 被拆成两条（一条说"没判空"，一条说"空指针崩溃"）。

```bash
python src/cli.py bank merge K-7Q2M K-3X9P
```

结果：保留 `K-7Q2M`，`merged_from` 加 `K-3X9P`，`found_by` 取并集。历史分重算时，两条的命中合并成一条。

### 7.2 拆分（split）

**场景**：一条 claim 里其实说了两个问题（"既没判空又没限流"）。

这个不做自动拆分。做法：人工在 bank 里新增一条，把原条目的 `note` 里注明"原条目含两个问题，已拆出 K-XXXX"。

### 7.3 平反（overturn）

**场景**：三个月后你发现某条被判 `rejected` 的其实是真 bug。

```bash
python src/cli.py bank overturn K-7Q2M --verdict confirmed --sev P1 --note "线上复现了"
```

结果：

- `verdict` 改为 `confirmed`
- `status` 改为 `active`
- **当初判 rejected 的裁判记录保留**（用于统计裁判准确率）
- 提交者从"误报"变"命中"，历史分重算

### 7.4 作废（deprecate）

**场景**：代码重构了，那条 bug 不存在了。

```bash
python src/cli.py bank deprecate K-7Q2M --note "v2 重写后该逻辑已删除"
```

结果：`status=deprecated`，不再参与 recall 分母，但历史 run 的分数不变（当时它确实存在）。

### 7.5 维护频率

| 操作 | 频率 | 触发条件 |
|---|---|---|
| merge | 每次 `bank sync` 后 | 聚类误拆 |
| split | 每轮人工复核时 | 一条多问题 |
| overturn | 随时 | 线上暴露 / 人工改判 |
| deprecate | 每次 `dataset_vN` 升级时 | 代码大改 |

## 八、bank 的初始化：第一次怎么建

第一轮没有 bank，怎么做？

```
r01: 全部走常规裁决（人工 + 裁判），得出 200 条判断
     ↓
     bank sync r01  → 写入 200 条，bank_version = 1
     ↓
r02（第 5 个模型）：撞库，命中 160 条，新增 40 条
     ↓
     bank hit r02 → 增量盲评 → bank sync
```

**关键**：r01 的 200 条必须是"裁决过"的，不能是"推断"的。用 `inferred_confirmed` 建库等于把幻觉固化成真相，后面所有撞库都会放大这个错误。

如果 r01 没做裁判，只有共识推断，那么 bank 里只能写 `verdict=inferred`，且这些条目在后续 run 里仍然需要重新裁决一次。这是"欠的债要还"。

---

## 九、一句话总结

**bank 的本质是把"一次性的判断"变成"可继承的判断"。**

它的价值不在第一次跑，而在第五次、第十次跑——那时候你已经不用再为 200 条 claim 逐条裁决，只需要看 30 条新的。
