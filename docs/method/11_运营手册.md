# 11 运营手册

> 给"三个月后再回来跑一次"的你写的。
> 假设你已忘记所有细节，只想知道：从零到出报告，敲哪些命令。

---

## 一、首次搭建（约 40 分钟）

### 1.1 环境确认

```bash
cd "<仓库根目录>"
python --version          # 3.10+
python src/cli.py demo    # 必须能跑通，这是健康检查
```

`demo` 的输出应该在 `reports/demo-001/` 下生成四个文件。跑不通就先别往下走。

### 1.2 扫项目

```bash
python src/cli.py scan "<你的项目目录>"
python src/cli.py scan "<另一个项目目录>" --depth 3
```

生成 `config/projects.suggested.toml`。打开它，按 `04` 第二节的四条原则挑 8–10 个，复制进 `config/projects.toml`。

### 1.3 填两个配置

`config/projects.toml` 每个项目四项必填：

```toml
id            # 短横线小写，如 t05-shadow
path          # 绝对路径，正斜杠
target_dirs   # 只填业务源码目录
std_seconds   # 300 小 / 600 中 / 900 大
```

`config/candidates.toml` 每个候选五项必填：

```toml
id       # 产品/模型，必须带版本号
product  # 产品名
model    # 模型名
vendor   # 厂商，去重靠它
enabled  # true
```

### 1.4 冻结题库

```bash
python src/cli.py new-run r01
python src/cli.py task t05-shadow
python src/cli.py task t06-xxx
# ... 每个项目一条
```

检查 `tasks/t05-shadow/meta.json` 的 `total_lines` 是否在 500–8000 之间。超了就回去调 `target_dirs` 或 `max_file_lines`。

### 1.5 冻完就不能改

```bash
python src/cli.py status r01
```

确认 10 个 task 都存在。此后 `projects.toml` 里的 `target_dirs` / `max_file_lines` 不许改——改了就要重建 task，等于换卷子。

## 二、一次完整评测（分四天）

### D1–D3：采集（每天一个候选，各 2 小时）

严格按 `04` 第四节的操作。每天结束时：

```bash
python src/cli.py status r01
```

三个数字要盯：

| 指标 | 合格线 |
|---|---|
| `collected / expected` | ≥ 90% |
| `ok` 占比 | ≥ 85% |
| 每个 task 的 `wall_seconds` | 中位数在 `std_seconds` 的 0.5–1.5 倍之间 |

### D4 上午：归一化与聚类（20 分钟）

```bash
python src/cli.py normalize r01
```

输出示意：

```
[NORMALIZE] r01
  candidates: 4  tasks: 10  files: 38
  claims: 214   rejected: 26 (12.1%)
  top reasons:
    over_limit:title     9
    file_not_found       7
    evidence_not_in_code 6
    bad_severity         4
```

拒收率 > 20% 要停下来看 `normalized/_issues.jsonl`。常见原因是提示词版本不对，或模型输出被截断。

```bash
python src/cli.py cluster r01
```

```
[CLUSTER] r01
  claims in : 214
  clusters  : 156
  merged    : 58 (27%)
  support dist: 1家=112  2家=31  3家=11  4家=2
```

`support=1` 占比 70% 左右是正常的——大部分发现只有一家提。

### D4 中午：裁决（60–90 分钟）

**先做人工队列**（因为人工优先于机器票）：

```bash
python src/cli.py verdicts r01
```

会生成 `runs/r01/judgments/queue.md`，只包含"独到 + P0/P1"的条目，通常 15–25 条。

逐条填 `human.jsonl`：

```jsonl
{"cluster_id":"K004","verdict":"confirmed","real_sev":"P1","reason":"空列表确实会崩"}
{"cluster_id":"K007","verdict":"rejected","real_sev":"P2","reason":"命名偏好，不是缺陷"}
{"cluster_id":"K011","verdict":"out_of_scope","real_sev":"P1","reason":"依赖库已知漏洞，不是本项目引入"}
```

**再做机器裁判**（可选，但推荐）：

```bash
python src/cli.py packets r01
# 把 packets/*.md 逐个发给裁判模型，回答存成 <cluster_id>.json
python src/cli.py votes r01 judge-claude runs/r01/judgments/votes/judge-claude
python src/cli.py votes r01 judge-glm    runs/r01/judgments/votes/judge-glm
```

裁判选择三条：不参赛、不同 vendor、至少两个。

### D4 下午：计分与报告（10 分钟）

```bash
python src/cli.py verdicts r01
python src/cli.py score r01
python src/cli.py report r01
```

产物：

| 文件 | 用途 |
|---|---|
| `reports/r01/report.md` | 主报告，先看这个 |
| `reports/r01/scores.csv` | 进 Excel 做透视 |
| `reports/r01/scatter.html` | 能力 × 成本散点 |
| `reports/r01/fix_list.md` | 待修清单（v1.0） |

### D4 傍晚：沉淀（5 分钟，v1.0）

```bash
python src/cli.py bank sync r01
python src/cli.py bank stat
```

```
[bank] t05-shadow  issues=28  confirmed=19  rejected=7  deprecated=2  v1
[bank] t06-xxx     issues=31  ...
[bank] 合计 214 条，覆盖 10 个项目，bank_version=1
```

## 三、月度复测（加一个新模型）

这是整套系统最省力的场景：**不用重跑老模型，不用重新裁决老条目。**

```bash
# 1. 加候选
#    编辑 candidates.toml，加一个新 [[candidate]]

# 2. 采集（2 小时，只跑新模型）
python src/cli.py new-run r02
python src/cli.py start r02 newvendor/newmodel t05-shadow
# ... 10 个项目

# 3. 归一化 + 撞库
python src/cli.py normalize r02
python src/cli.py bank hit r02
```

`bank hit` 输出：

```
[bank hit] r02 newvendor/newmodel
  claims        : 52
  hit confirmed : 31  (59.6%)
  hit rejected  : 9   (17.3%)
  unmatched     : 12  (23.1%)   ← 需要增量盲评
  已更新 found_by 31 条，独到降级 4 条
```

```bash
# 4. 只裁决那 12 条
python src/cli.py packets r02 --only <12个ID>
# ... 发给裁判
python src/cli.py votes r02 judge-claude ...
python src/cli.py verdicts r02
python src/cli.py bank sync r02       # 新条目入库，bank_version=2

# 5. 重算全部历史（秒级）
python src/cli.py score r01
python src/cli.py score r02
python src/cli.py trend --metric rate_score
```

**关键**：第 5 步的 `score r01` 是必须的——因为 bank 变了（新增 12 条、4 条独到降级），r01 的 `score_now` 要重算。这一步不重跑模型，只重算。

## 四、报告怎么读

### 4.1 第一页：排行榜

```
第 1 名  workbuddy/claude-sonnet-5.5   rate 46.9  raw 34.5
第 1 名  kimi/kimi-k2.5                rate 45.2  raw 33.8   ← 分差 1.7，判并列
第 3 名  kimicode/glm-5.5              rate 38.1  raw 29.2
第 4 名  workbuddy/deepseek-v4.1-flash rate 31.4  raw 24.0
```

三件事注意：

1. **并列**：分差 <2 就是并列，不要读成 1、2、3
2. **两个分**：`rate` 是率化分（跨 run 可比），`raw` 是绝对分（本次贡献）。方向不一致时以 `rate` 为准
3. **第四名不代表最差**：可能只是它最保守（报得少）

### 4.2 第二页：分项

| 列 | 含义 | 什么时候看 |
|---|---|---|
| `hits_weighted` | 加权命中 | 看"找得多不多" |
| `false_pos` | 误报数 | 看"报得准不准" |
| `unique` | 独到命中 | 看"有没有别人没发现的" |
| `missed_p0` | 漏掉的 P0 数 | 最该看的指标 |
| `median_seconds` | 中位耗时 | 看"快不快" |

**`missed_p0` 是最容易被忽略、但最重要的列。** 一个模型报了一堆 P2、漏了两个 P0，它的总分可能不低，但对你毫无价值。

### 4.3 第三页：散点图

横轴成本（token 或耗时），纵轴得分。四个象限：

```
高分低成本 ← 优先用
高分高成本 ← 关键时刻用
低分低成本 ← 日常凑合用
低分高成本 ← 别用
```

### 4.4 待修清单（v1.0）

```markdown
# r01 待修清单（A 级）

## P0 · 3 条

### 1. 库存扣减非原子，并发下单会超卖
- 位置：apps/api/src/orders/service.ts:142
- 触发：两个请求同时下单同一 SKU，库存刚好够一个
- 后果：超卖，库存为负
- 证据：E1（复现测试跑红）
- 发现者：claude-sonnet-5.5 独到
```

按严重度排序，标证据级别，标是否独到。可以直接当待办用。

## 五、故障排查

| # | 现象 | 原因 | 处理 |
|---|---|---|---|
| 1 | `demo` 跑不通 | 代码改动破坏了兼容 | 先修 demo，再谈其他 |
| 2 | `normalize` 报 `json_parse_error` | 模型输出不是 JSON | 看 raw 文件；提示词版本对不对 |
| 3 | 拒收率 > 30% | 提示词与解析器不匹配 | 检查 `prompt_version` 与 `rubric_vN` |
| 4 | 聚类数 = claim 数的 95% | 聚类太严 | 增大 `line_window` |
| 5 | 聚类数 < claim 数的 40% | 聚类太松（误合） | 减小 `line_window`，提高标识符要求 |
| 6 | 某候选全是 uncertain | 裁判与它同族 | 换裁判 |
| 7 | `score` 结果与上次差很多 | 看 `08` 第五节的六种漂移来源 | 对照 `run.json` 的四个版本号 |
| 8 | `bank hit` 命中率 < 40% | 两种可能：新模型强 / 新模型乱报 | 抽 10 条人工看 |
| 9 | `trend` 拒绝画图 | 版本号不一致 | 正常行为，先统一版本 |
| 10 | 报告里 rate_score 是 null | 题库未成型（<20 条或覆盖 <0.8） | 先跑一轮完整裁决建库 |

### 5.1 一个万能排查顺序

任何"分数不对劲"，按这个顺序查，5 分钟内能定位：

```
1. score → 看 raw_score 是否合理（数量级对不对）
2. scores.jsonl → 逐条看，有没有明显该命中却没命中的
3. verdicts.jsonl → 那条的 verdict 是什么？为什么
4. queue.md → 是不是还在等人判
5. human.jsonl / votes/ → 有没有裁决但没被读到
6. origin.jsonl → 归属对不对（有没有张冠李戴）
7. raw/ → 原始回复是不是本身就有问题
```

## 六、参数调优

只调这四个，其他的别动：

| 参数 | 什么时候调 | 怎么调 |
|---|---|---|
| `weights.severity` | 觉得"P0 不够重" | P0 从 8 → 10，必须全部重算 |
| `false_positive_penalty` | 误报太多/太少 | 0.5 → 0.8（更严）或 0.3（更松） |
| `judge.consensus_ratio` | 共识太松/太严 | 0.5 → 0.67（要求更多家） |
| `clustering.line_window` | 误合/误拆 | 8 → 5（更严）或 12（更松） |

**调参三条铁律**：

1. 一次只调一个
2. 调完必须 `score` 全部历史 run，看排名变化
3. 排名变化 > 一个名次，说明这个参数很敏感，记录下来

不要调的：`min_findings`（改了会破坏"防沉默"设计）、`unique_bonus`（改了会让独到发现失衡）、`chars.*`（改了要重跑采集）。

## 七、季度维护清单

| 项 | 频率 | 耗时 |
|---|---|---|
| 备份 `config/.salt` | 每次改配置后 | 1 分钟 |
| 归档旧 run（tar） | 每季度 | 5 分钟 |
| 检查 `bank` 里有没有该 deprecate 的 | 每季度 | 20 分钟 |
| 重新校准 `std_seconds` | 每季度 | 10 分钟 |
| 跑一次 `demo` | 每次改代码后 | 1 分钟 |
| 看一次 `trend` | 每季度 | 5 分钟 |

### 7.1 季度复盘的三问

1. **这一季度有哪条 bank 条目被线上验证了？** → 说明这套系统真的在帮你
2. **有哪条被判 rejected 后来又复现了？** → 说明裁判或人工判错了，要平反
3. **新模型的命中率是多少？** → <40% 说明题库该扩充了
