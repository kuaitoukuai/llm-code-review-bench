# 05 匿名化与双盲

> "把名字删掉"只是双盲的第一步，而且是最弱的一步。
> 这一篇讲清楚**身份是怎么泄漏的**，以及在哪一层拦截最划算。

---

## 一、身份泄漏的三个渠道

| # | 渠道 | 怎么泄漏 | 现有防护 | 残余风险 |
|---|---|---|---|---|
| 1 | **显式标识** | 文件名带模型名、报告里写"我是 Claude" | `pool/origin` 分离 | 低（已解决） |
| 2 | **文风指纹** | 用词偏好、句式、markdown 习惯、分类术语 | 无明显防护 | **高** |
| 3 | **字段指纹** | 固定字段里的独特写法（如总把 severity 写 `P1（高）`） | 枚举归一化 | 中 |

### 渠道 2 有多严重

公开研究给的量级：仅删除模型名称（弱身份模糊化）对自我偏爱的缓解**不显著**——模型仍能通过文风识别自己的输出。这就是为什么需要"作者混淆"这一层。

但这里有个反直觉的结论要先说：**作者混淆的收益没有想象中大，成本却不低。**

- 收益：可能把裁判的自我偏爱从 20% 降到 10%，但没人测过在代码审查场景下的具体数字
- 成本：改写会污染 `evidence` 与代码原文的对应关系，导致"可核验性"下降；改写本身要花 3–5 分钟/份；改写还会引入语义漂移，把一条 P1 改成 P2

所以本方案的立场是：**L1 必做，L2 选做且要先做 A/B 验证，L3 只在研究场景做。**

---

## 二、三档匿名方案

### L1 基础匿名（默认，零成本）

| 措施 | 实现 | 防哪个渠道 |
|---|---|---|
| 去名字 | 保存时不写 candidate，只写匿名 ID | 渠道 1 |
| 独立文件 | 一条 claim 一个文件，不打包成"某模型的报告" | 渠道 1、3 |
| 统一字段 | 全部走 10 字段，禁自由发挥 | 渠道 3 |
| 枚举归一 | `P1（高）` → `P1`，`critical` → `P0` | 渠道 3 |
| 去支持度 | 包里不含 `support_count` | 从众偏差 |
| 去提交者严重度 | 包里不给提交者声称的 severity | 锚定偏差 |

L1 已经能挡住 80% 的显式泄漏，且完全不需要额外计算。

### L2 作者混淆（可选实验）

只对**三个描述性字段**做同义替换，**绝不碰** `file` / `line` / `evidence`：

| 字段 | 可否混淆 | 理由 |
|---|---|---|
| `title` | ✅ 可 | 描述性，替换后语义不变 |
| `trigger` | ✅ 可（谨慎） | 换词可能改变触发条件的精确度 |
| `impact` | ✅ 可 | 后果描述，替换安全 |
| `file` / `line` / `line_end` | ❌ 禁止 | 定位信息，改了就没法核验 |
| `evidence` | ❌ 禁止 | 必须与代码原文一致，改了 `evidence_not_in_code` 直接拒收 |
| `severity` / `category` | ❌ 禁止 | 枚举，改了等于改分 |

替换规则示例（本地词典，不调模型）：

| 原表述 | 混淆后 |
|---|---|
| 存在空指针风险 | 有潜在的空引用 |
| 索引越界 | 下标溢出边界 |
| 未做防御 | 缺少前置校验 |
| 并发竞态 | 并行访问冲突 |
| 资源泄漏 | 句柄未释放 |

**前置条件**：跑一次作者识别率实验（见第七节），确认识别率从 >50% 降到 <30% 才值得开。

### L3 全字段改写（研究场景）

用另一个模型把整条 claim 重写一遍。问题：

- 重写者本身可能带偏好
- 重写后 `evidence` 与代码对不上
- 成本高（每条一次调用）

**不建议在 v1.0 之前做。**

## 三、盐哈希 ID 的实现

### 3.1 为什么不用顺序 ID

顺序 ID（`K001`、`K002`）有两个问题：

1. **可推断顺序**：裁判看到 `K001` 和 `K017`，能猜到"这是第 1 条和第 17 条"，而顺序往往对应文件顺序，间接泄漏了提交者
2. **跨 run 不稳定**：换一次评测，`K001` 就指向另一条了，没法做题库

### 3.2 实现

```python
# src/anon.py
import hmac, hashlib, base64, secrets, json
from pathlib import Path

SALT_FILE = Path("config/.salt")

def make_salt(path=SALT_FILE):
    """生成一次，之后永久复用。丢了 = 所有 issue_id 失效。"""
    if not path.exists():
        path.write_text(secrets.token_hex(32), encoding="utf-8")
    return bytes.fromhex(path.read_text(encoding="utf-8").strip())

def anon_id(seed: str, salt: bytes, nbytes: int = 5) -> str:
    """稳定、不可反推、跨 run 一致"""
    mac = hmac.new(salt, seed.encode("utf-8"), hashlib.sha256).digest()
    # base32 去掉易混字符 I/O/0/1
    s = base64.b32encode(mac).decode().replace("=", "")
    s = s.translate(str.maketrans("IO01", "WKLM"))
    return s[:nbytes]

def claim_seed(proj: str, file: str, anchor_line: int, category: str) -> str:
    return f"{proj}|{file}|{anchor_line}|{category}"
```

生成的 ID 形如 `K-7Q2M`，4 位 base32 = 32^4 ≈ 100 万种组合。10 个项目 × 每项目 50 条 = 500 条，碰撞概率约 0.1%，可接受。

> **`config/.salt` 必须进 git 且只此一份。** 丢了之后所有历史 `issue_id` 全变，题库作废。备份到第二个地方。

### 3.3 三个必须

| 必须 | 原因 |
|---|---|
| 盐文件只此一份，且备份 | 换盐 = 全部 ID 变化 = 题库作废 |
| ID 生成函数不能改算法 | 同上 |
| ID 不进裁判包之外的公开材料 | 避免被反推 |

## 四、裁判包的构造

### 4.1 一个包只有一条 claim

```markdown
# 待判定问题

## 代码（apps/api/src/orders/service.ts 第 130–175 行）

```ts
130  async function createOrder(userId, items) {
...
142    const stock = await repo.getStock(item.sku);
143    if (stock.quantity >= item.qty) {
144      await repo.deduct(item.sku, item.qty);
...
```

## 待判定声明

- **文件**：apps/api/src/orders/service.ts
- **行号**：142–150
- **问题**：库存扣减与判断之间没有原子性保护
- **触发条件**：两个请求同时下单同一 SKU，且库存刚好等于其中一个的数量
- **后果**：超卖，库存变负数
- **代码证据**：`if (stock.quantity >= item.qty) { await repo.deduct(...) }`

## 你的任务

判断上面这条声明是否成立。只回答 JSON：

{"verdict":"confirmed|rejected|out_of_scope|trivial|uncertain","real_sev":"P0|P1|P2|P3","reason":"≤60字"}
```

### 4.2 包里绝对不能出现的字段

| 字段 | 为什么不能出现 |
|---|---|
| `candidate` / `model` / `product` | 自我偏爱 |
| `support_count` / `found_by` | 从众偏差 |
| 提交者声称的 `severity` | 锚定偏差 |
| 同批其他 claim | 位置偏差、整体印象 |
| 提交者的 `title` 原文 | 文风指纹（可选：用混淆后的版本） |

### 4.3 代码上下文的取法

`config/system.toml` 里 `context_lines = 60`，即 claim 行号上下各 60 行。

为什么要给这么宽的上下文：只给 bug 所在那一行，裁判无法判断"上游是否已经校验过"。但也不能给整个文件——超过 300 行，裁判的注意力会散，且容易"顺手"评论别的地方。

经验值：**上下文行数 ≈ 20 + 3 × 跨行范围**，最少 40 行，最多 120 行。

## 五、顺序双评（抗位置偏差）

### 5.1 位置偏差有多强

同一对答案换个顺序，判决就变。代码类两两比较可达 10 个百分点以上，个别模式影响 40% 的评估。

本系统的裁判是"单条判定"而非"两两比较"，位置偏差理论上更小，但仍存在**呈现顺序效应**（比如先看代码再看声明 vs 先看声明再看代码）。

### 5.2 做法

同一个包生成两个版本：

| 版本 | 结构 |
|---|---|
| 正序 | 代码在上，声明在下 |
| 反序 | 声明在上，代码在下 |

两次结论：

| 情况 | 处理 |
|---|---|
| 一致 | 采纳，计 1 票 |
| 不一致 | 标 `unstable`，不计票，进人工队列 |

**成本**：裁判调用量翻倍。对 200 条 claim × 3 裁判 = 600 次，翻倍到 1200 次。

**收益**：把"位置偏差导致的误判"从统计里剔除。对独到发现（只有一家提）尤其重要——这类条目本来就靠一票定生死。

### 5.3 什么时候可以不做

- 候选 ≤3 且差距明显（极差 > 25%）→ 位置偏差改变不了名次
- 只做"共识推断"不做裁判 → 无位置偏差可言

建议：**首轮做，之后按需做**。首轮做是因为要校准裁判的稳定性，这个数据本身有价值。

## 六、裁判的选择

| 规则 | 内容 | 违反的后果 |
|---|---|---|
| R1 | 裁判不得是参赛候选 | 自我偏爱 |
| R2 | 至少 2 个不同 vendor | 同族一致率虚高 5–7pt |
| R3 | 单条 claim 的 `panel_size = 3` | 两票平局无法裁决 |
| R4 | 裁判模型本身也记入 `candidates.toml`（`enabled=false`） | 无法审计"谁判的" |
| R5 | 人工裁决永远优先于机器票 | 机器裁判与人类一致率只有 60–68% |

### 6.1 一个现实问题：候选只有 4 个，裁判从哪来

如果 4 个候选已经覆盖 4 个 vendor，那就没有"非参赛"的 vendor 了。三个解法：

| 解法 | 做法 | 代价 |
|---|---|---|
| A. 引入第 5 个 vendor 专做裁判 | 加一个不参赛的模型（如 GPT/Gemini 系） | 多一个 API 账号 |
| B. 用本地模型做裁判 | 本地跑一个中等模型（如 Qwen 32B） | 质量不稳定，但完全不参赛 |
| C. 只做人工 | 15–25 条 × 2 分钟 = 40 分钟 | 最可靠，但不可扩展 |

**推荐 A + C 组合**：机器裁判用第 5 个 vendor，人工只过"独到发现 + P0/P1 争议"。这样既保证跨族，又保证关键条目有人看过。

## 七、自检：作者识别率实验

这是验证"匿名到底有没有用"的唯一方法。做法很简单，20 分钟能跑完。

### 7.1 步骤

1. 从上一轮 run 里取 10 条 claim，已知作者（从 `origin.jsonl` 查）
2. 构造两组材料：
   - **A 组**：L1 匿名后的文本（去掉模型名）
   - **B 组**：L1 + L2 混淆后的文本
3. 让一个**不参赛**的模型做选择题："这 10 条分别最可能出自以下 4 个模型中的哪一个？"
4. 算准确率

### 7.2 判读

| 准确率 | 含义 | 行动 |
|---|---|---|
| ≈ 25%（随机水平） | 完全无法识别 | L1 足够，不必上 L2 |
| 25%–50% | 弱识别 | L2 有价值，做 A/B 对比 |
| > 50% | 强识别 | 必须上 L2，且检查字段指纹 |
| > 75% | 泄漏 | 停下来查：是不是 `pool.jsonl` 里还带着来源字段 |

### 7.3 这个实验的副产品

跑完你会得到"哪些模型最好认"的排序。这个信息本身很有用——文风最独特的模型，在双盲里最吃亏（因为裁判更容易认出它并偏爱/打压它）。

## 八、双盲的边界：它解决不了什么

| 问题 | 双盲能解决吗 | 说明 |
|---|---|---|
| 自我偏爱 | 部分 | 去掉名字能削弱，但文风仍可识别 |
| 同族给高分 | 部分 | 靠"裁判跨 vendor"解决，不靠匿名 |
| 从众偏差 | 是 | 只要包里不带 `support_count` |
| 锚定偏差 | 是 | 只要剥离提交者声称的 severity |
| 位置偏差 | 是（用顺序双评） | 但成本翻倍 |
| **训练语料同质** | **否** | 所有模型都读同一批 GitHub 代码，会犯同样的错，匿名无能为力 |
| **裁判能力不足** | **否** | 裁判自己看不懂的问题，匿名与否都判不对 |

最后两条是结构性的，只能靠"人工抽检 + 执行复现"补，不能靠匿名补。
