# 03 数据契约

> 这份文件是"法律条文"。所有脚本都按它校验，所有争议都以它为准。
> 改动任何字段 = 升 `rubric` 版本 = 历史分数标注不可比。

---

## 一、为什么必须强制字段

自由文本报告有四个致命问题，每一个都会让排名失真：

| 问题 | 表现 | 字段化怎么解决 |
|---|---|---|
| **能言善辩** | 写得长、写得自信的得分高 | 字段有字数上限，超限整条作废；没有"总结"字段 |
| **凑数** | 报 30 条，蒙中 2 条 | 单题上限 12 条；误报扣分；最少 3 条兜底 |
| **不可核验** | "这里可能有并发问题"——指不到行 | `file` + `line` 必填，`evidence` 必须引用代码原文 |
| **不可统计** | 一段散文，没法按类别聚合 | `severity` / `category` 枚举化，可 group by |

一句话：**把"写作能力"从评分维度里删掉。**

## 二、作答契约（review）

### 2.1 完整字段表（10 字段）

| # | 字段 | 类型 | 必填 | 上限 | 说明 | 违反后果 |
|---|---|---|---|---|---|---|
| 1 | `file` | string | ✅ | — | 必须与代码块 `FILE:` 后路径完全一致 | 找不到文件 → 整条拒收 |
| 2 | `line` | int | ✅ | — | 起始行号，以代码块左侧标注为准 | 非正整数 → 拒收 |
| 3 | `line_end` | int\|null | ⬜ | — | 结束行号，跨行问题时填 | 小于 `line` → 置 null |
| 4 | `severity` | enum | ✅ | — | `P0`/`P1`/`P2`/`P3` | 无法归一 → 拒收 |
| 5 | `category` | enum | ✅ | — | 见 2.3 | 无法归一 → 归 `other`，不拒收 |
| 6 | `title` | string | ✅ | **40 字** | 一句话说清是什么问题 | 超限 → 整条拒收 |
| 7 | `trigger` | string | ✅ | **120 字** | 什么输入/条件下触发 | 超限 → 整条拒收 |
| 8 | `impact` | string | ✅ | **120 字** | 造成什么后果 | 超限 → 整条拒收 |
| 9 | `evidence` | string | ✅ | **60 字** | **引用出问题的代码原文片段**（新增） | 空 → 整条拒收 |
| 10 | `verify_hint` | string | ✅ | **80 字** | 怎么快速验证 | 超限 → 整条拒收 |

可选扩展（仅 `review_v2`，`rubric_v2` 起生效）：

| 字段 | 类型 | 上限 | 说明 |
|---|---|---|---|
| `repro` | string | 12000 字 | 一个能跑红的最小复现测试；进执行通道 |

### 2.2 为什么不加 `suggestion`

`R6` 明确要求"只检查 bug 不修改代码"。加上 `suggestion` 会带来两个副作用：

1. 模型把精力放在"怎么写修复"上，挤占"定位问题"的注意力
2. 修复建议本身会被当成质量信号（写得好的加分），这是典型的冗长偏差

修复方向留给报告生成时由人判断，或由 `fix_list.md` 用 `title + trigger` 拼出来。

### 2.3 枚举定义

**severity（四档）**

| 值 | 判定标准 | 权重（v0.2 起） |
|---|---|---|
| `P0` | 数据损坏 / 资金损失 / 越权访问 / 安全漏洞 / 核心功能不可用 | 8 → 见 `07` |
| `P1` | 正常路径下用户可见的功能错误、明显崩溃 | 4 |
| `P2` | 边界条件未处理、异常路径崩溃、错误处理缺失 | 2 |
| `P3` | 可维护性、命名、注释、重复代码（**不计分，只记录**） | 0 |

注意：`P3` 在 v0.1 里计 1 分，本方案建议**改成 0 分但保留记录**。理由见 `07` 第五节——风格类问题的判定方差最大，给它分数等于给噪声加权。

**category（六类）**

| 值 | 含义 | 与 v0.1 的映射 |
|---|---|---|
| `correctness` | 逻辑错误、结果不对 | 同名 |
| `security` | 注入、越权、密钥泄漏、路径穿越 | 同名 |
| `reliability` | 空值、越界、异常未捕获、资源泄漏 | 同名 |
| `concurrency` | 竞态、死锁、非原子更新 | 新增（从 reliability 拆出） |
| `performance` | 明确的性能缺陷（有触发条件） | 同名 |
| `maintainability` | 可维护性（默认不计分） | 同名 |
| `other` | 无法归类 | 兜底 |

`concurrency` 单独拆出来的理由：这类问题的 `trigger` 极难描述清楚，聚类时也最容易被误合并，单独一类便于人工复核时批量看。

### 2.4 输出格式

只允许一个 JSON 数组，外层可有 ```json 代码块。允许空数组 `[]`。

```json
[
  {
    "file": "services/parser.py",
    "line": 148,
    "line_end": 152,
    "severity": "P1",
    "category": "reliability",
    "title": "空列表输入时未防御导致索引越界",
    "trigger": "调用 parse_sections([]) 时 sections[0] 取不到元素",
    "impact": "抛出 IndexError，解析流程中断，接口返回 500",
    "evidence": "return sections[0].strip()",
    "verify_hint": "传入不含任何章节的文档后调用解析函数"
  }
]
```

### 2.5 校验伪代码

```python
def validate(item, code_index, limits):
    errs = []
    # 1. 必填
    for f in ("file", "line", "severity", "title", "trigger", "impact", "evidence"):
        if not item.get(f):
            errs.append(f"missing:{f}")

    # 2. 定位可核验
    path = norm_path(item.get("file"))
    if path not in code_index:
        errs.append("file_not_found")
    else:
        n = code_index[path]["lines"]
        if not (1 <= norm_line(item.get("line")) <= n):
            errs.append("line_out_of_range")
        if item.get("line_end") and not (item["line"] <= item["line_end"] <= n):
            item["line_end"] = None

    # 3. 枚举归一
    sev = norm_severity(item.get("severity"))
    if sev is None:
        errs.append("bad_severity")

    # 4. 字数上限（按字符数，不按字节；中文算 1 个）
    for f, cap in limits.items():
        if char_len(item.get(f, "")) > cap:
            errs.append(f"over_limit:{f}")

    # 5. 反空话：evidence 必须能在对应行附近找到
    if not evidence_in_code(item.get("evidence"), code_index.get(path), item.get("line")):
        errs.append("evidence_not_in_code")

    return errs
```

`evidence_not_in_code` 这条是本方案新增的**最强约束**：模型必须引用真实存在的代码片段。它同时干掉三种情况——幻觉引用的、编造行号的、说"大概在这附近"的。

实现上做宽松匹配：去掉空白、统一引号、允许 3 处字符差异（OCR 式的容错），匹配窗口为 `line ± 5` 行。

## 三、裁决契约（judge）

### 3.1 六类标签

| 标签 | 定义 | 计分影响 |
|---|---|---|
| `confirmed` | 代码证据与触发路径都成立 | 命中，按 `real_sev` 加权 |
| `rejected` | 理解错误 / 触发条件不成立 / 与代码矛盾 | 误报，扣分 |
| `out_of_scope` | 可能成立，但不是本次代码引入，或超出审查范围 | 不计命中，**也不计误报** |
| `trivial` | 基本属实，但没有实际修复价值 | 计 0.5 个命中（可选，默认 0） |
| `uncertain` | 证据不足，无法确认 | 待定，不奖不罚；进仲裁或人工 |
| `duplicate` | 与另一条已裁决条目重复 | 合并到主条目，不单独计分 |

`out_of_scope` 这一类的价值：防止"模型报了一堆依赖库的已知 CVE"被当成误报扣分，也防止它们被当成有效发现加分。它是一条**中立通道**。

### 3.2 裁判输出格式

```json
{
  "verdict": "confirmed",
  "real_sev": "P1",
  "reason": "sections 为空时确实直接取下标，无防御",
  "confidence": 0.85
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `verdict` | ✅ | 六类之一 |
| `real_sev` | ✅ | 裁判独立判断的严重度，**不看提交者声称的档位** |
| `reason` | ✅ | ≤60 字，只说"为什么"，不许复述问题 |
| `confidence` | ⬜ | 0–1，可选；用于加权投票（默认等权） |

**关键约束：裁判看不到提交者声称的 severity。** 裁判包里只给 `file/line/evidence/trigger/impact`，`severity` 字段被剥离。否则会被锚定。

### 3.3 裁决合并规则

| 情况 | 结果 |
|---|---|
| ≥2 票 `confirmed`，0 票 `rejected` | `confirmed`，`real_sev` 取中位数 |
| ≥2 票 `rejected` | `rejected` |
| 1 确认 + 1 拒绝 | `uncertain` → 进仲裁（第三票或人工） |
| 全是 `uncertain` | `uncertain` → 高严重度进人工，低严重度归档 |
| 有 `duplicate` | 先合并，再按合并后条目重算 |
| 无票（未做裁判） | 走共识推断：`support_vendor >= 2` → `inferred_confirmed`（弱证据） |

`inferred_confirmed` 是独立标签，不能与 `confirmed` 混用——报告里必须分开统计，因为它没有经过独立裁决。

## 四、沉淀题库契约（bank）

### 4.1 一行一条 issue

```json
{
  "issue_id": "K-7Q2M",
  "proj": "t05-shadow",
  "file": "apps/api/src/orders/service.ts",
  "line": 142,
  "line_end": 150,
  "category": "concurrency",
  "verdict": "confirmed",
  "real_sev": "P1",
  "found_by": ["kimi/kimi-k2.5", "workbuddy/claude-sonnet-5.5"],
  "first_seen": "r01",
  "last_seen": "r03",
  "bank_version": 3,
  "status": "active",
  "merged_from": ["K-3X9P"],
  "evidence_digest": "sha1:8f2c...",
  "note": "库存扣减非原子，重复提交会超卖"
}
```

| 字段 | 说明 |
|---|---|
| `issue_id` | `K-` + 4 位 base32，由 `proj+file+line+category` 的 HMAC 生成；同一条目在不同 run 里必须稳定 |
| `verdict` | `confirmed` / `rejected` / `out_of_scope` / `trivial` |
| `real_sev` | 裁决后的真实严重度（不是提交者声称的） |
| `found_by` | 发现者列表（含历史），用于算独到加成 |
| `status` | `active` / `deprecated` / `merged` / `overturned`（平反） |
| `merged_from` | 被合并进来的旧 ID，保证历史可追溯 |
| `evidence_digest` | 代码片段哈希，代码变更后用于判断"这条是否还成立" |

### 4.2 为什么 `issue_id` 不能只用行号

行号会漂移。改一行代码，下面所有行号 +1，ID 全变，历史分数立刻失效。

所以 `issue_id` 的生成规则是：

```
seed = proj + "|" + normalized_file + "|" + anchor_line + "|" + category
anchor_line = 该 claim 覆盖范围内，第一行包含函数定义/关键标识符的行
issue_id = "K-" + base32(hmac_sha256(seed, salt))[:4]
```

`anchor_line` 用"锚点行"而不是"起始行"，能在上下文增删时保持稳定（只要函数还在）。

## 五、配置契约

### 5.1 `projects.toml`（题库）

```toml
[[project]]
id = "t05-shadow"
path = "<你的项目路径>"
target_dirs = ["apps/api/src", "apps/web/src"]
exclude = ["**/node_modules/**", "**/dist/**", "**/*.min.js"]
max_file_lines = 800
std_seconds = 600          # 单项目标准耗时（秒），固定不随参赛集合浮动
snapshot = "eval_repos/t05-shadow"   # 可选，只读快照
enabled = true
```

`std_seconds` 是本方案新增的**固定基准线**，替代 v0.1 的"全局中位耗时"。原因见 `07` 第六节。

### 5.2 `candidates.toml`（候选）

```toml
[[candidate]]
id = "kimi/kimi-k2.5"
product = "Kimi Code"
model = "kimi-k2.5"
vendor = "moonshot"        # 判"是否同族"只看这个字段
enabled = true
note = "CLI 订阅，token 取不到精确值"
```

`vendor` 是去重的唯一依据。填错会导致支持度虚高——三个同厂模型被算成三家。

### 5.3 `run.json`（一次评测）

```json
{
  "run_id": "r01",
  "created": "2026-11-14T02:10:00+08:00",
  "note": "首轮 10 项目 4 候选",
  "dataset_version": "dataset_v1",
  "rubric_version": "rubric_v2",
  "prompt": "review_v2",
  "bank_snapshot": 0,
  "projects": ["t05-shadow", "t06-xxx"],
  "candidates": ["kimi/kimi-k2.5", "workbuddy/claude-sonnet-5.5"]
}
```

`bank_snapshot` 记录这次评测用的是银行第几版。0 表示还没建库。这一条是"当时分"能算出来的前提。

### 5.4 `run_logs.jsonl`（计时）

```json
{"run":"r01","candidate":"kimi/kimi-k2.5","task":"t05-shadow","repeat":1,
 "start":"2026-11-14T02:12:03+08:00","end":"2026-11-14T02:21:47+08:00",
 "wall_seconds":584,"token_in":45000,"token_out":3200,"status":"ok"}
```

`status`：`ok` / `timeout` / `aborted` / `retry`。超时的记录仍进统计，但打标。

## 六、版本号规则

四个版本号，各自独立演进：

| 版本 | 管什么 | 什么时候升 | 升了之后 |
|---|---|---|---|
| `dataset_vN` | 题库：哪些项目、哪次快照、golden 集 | 增删项目、更新快照、改埋点 | 旧 run 标注"数据集不同，不可直接横比" |
| `rubric_vN` | 提示词 + 字段 + 校验规则 | 改提示词、加字段、改上限 | 必须重跑 `normalize`（因为解析规则变了） |
| `bank_vN` | 沉淀题库的状态版本 | 每次 `bank sync` / 平反 / 合并 | 触发 `score_now` 重算 |
| `scoring_vN` | 评分公式与权重 | 改权重、改公式 | 只重跑 `score`，不动上游 |

**兼容矩阵**：

| dataset | rubric | 分数可比？ |
|---|---|---|
| 同 | 同 | ✅ 直接比 |
| 同 | 不同 | ⚠️ 需用新 rubric 重算才可比 |
| 不同 | 同 | ⚠️ 只能按项目交集比，且标注 |
| 不同 | 不同 | ❌ 不可比，只能看趋势 |

## 七、字段变更的迁移成本

| 变更 | 影响 | 成本 |
|---|---|---|
| 加可选字段（如 `repro`） | 旧数据缺字段 → 置 null | 低，`normalize` 兼容 |
| 加必填字段（如 `evidence`） | 旧数据全部不合规 | **高**，必须重跑采集 |
| 改字数上限 | 旧数据可能超限 | 中，重跑 `normalize` |
| 改枚举值（加 category） | 旧数据映射到 `other` | 低 |
| 改 `issue_id` 生成规则 | **题库全部失效** | **极高**，禁止 |

最后一条要写进代码注释：`issue_id` 的生成算法一旦上线就不能改，要改就整体重建 bank 并升 `dataset_vN`。
