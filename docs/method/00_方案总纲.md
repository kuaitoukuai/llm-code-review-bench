# 00 方案总纲

## 一、目标

**一句话**：在自有代码上，用两小时、十个项目，得到一份"哪家产品里的哪个模型最会找我这类 bug"的排序，并且这份排序在半年后加入新模型时依然有效、可被追溯、可被重算。

拆成三个可交付物：

| # | 交付物 | 判定标准 |
|---|---|---|
| D1 | **一份当前榜单** | 8–10 个项目 × 3–5 个候选，含加权命中、误报、独到发现、耗时四个维度 |
| D2 | **一套可复用题库** | 每个项目一份 `bank/<proj>_bank.jsonl`，记录每条已裁决缺陷的真伪、真实严重度、发现者列表 |
| D3 | **一套可重算的规则** | 改权重/改公式/补裁决后，一条命令重算全部历史分数，不重跑任何模型 |

D1 是这一轮要用的，D2 是下一轮省时间的关键，D3 是这套系统区别于"一次性横评"的根本。

## 二、五个硬约束

来自你的原始需求（见 `_sources/U0_原始需求与前提假设.md`），逐条列出，因为后面每个设计决定都要对着它们解释。

| # | 约束 | 原文/来源 | 对设计的强制影响 |
|---|---|---|---|
| C1 | **项目不超过 10–30 个** | "我自己的项目 10-30 个左右" | 题库规模小 → 不能用统计显著性说话 → 只能做粗排 + 并列判定 |
| C2 | **单模型总耗时不超过 2 小时** | "每个大模型检查不超过 2 小时" | 单项目预算 10–12 分钟，必须有硬边界与超时保存 |
| C3 | **没有人工金标准** | "没有现成的、人工复核过的 git 修改答案" | 召回率没有真分母 → 只能用"交叉验证答案集"+ 埋点补充 |
| C4 | **系统可复用、历史分数有效** | "以后想增加新大模型测试……曾经测评数据、评分依然可用" | 必须有冻结快照、沉淀题库、双版本号、重算能力 |
| C5 | **暂不区分产品与模型** | "主要使用 kimiCode、workbuddy 中的不同大模型" | 候选记作 `产品/模型`，报告里标注"组合能力" |

另有四条软约束（影响打分口径，不改变架构）：

- 找错 bug 适当负分（→ 误报惩罚，系数 0.5）
- 检查时间长适当负分、以正确率为主（→ 时间封顶 5%）
- 强制格式化输出、单列检查结果（→ 强制 JSONL，8–10 字段）
- 防自我偏爱 / 同族给高分 / 凑数 / 能言巧辩（→ 双盲 + 字段上限 + 最少条数）

## 三、五个设计决定

这五条是整份方案的骨架。每条都给出"为什么这么定"和"代价是什么"——因为代价迟早会显现，先写下来，免得后面误以为是 bug。

### 决定 1：最小单位是"一条缺陷"，不是"一份报告"

| 项 | 内容 |
|---|---|
| **做法** | 每份作答先归一化成 JSONL，一行一条 claim；后续去重、匿名、裁决、计分全部以 claim 为单位 |
| **为什么** | ① 整篇互评无法复用（换个模型就得重跑）② 无法定位"哪一条被判错了"③ 无法做"同一处问题被两家都报了"的合并 ④ 无法让裁判只看一条，必然产生位置偏差与冗长偏差 |
| **代价** | 归一化会丢信息（上下文、语气、整体判断）；聚类永远是近似的，会误合/误拆 |
| **缓解** | 归一化保留 `raw_ref`（回指原始回复的行号区间）；聚类误判可通过人工队列修正 |
| **落点** | `pipeline.normalize` → `pipeline.cluster`（v0.1 已实现） |

### 决定 2：原始层不可变，其余全部可重算

| 项 | 内容 |
|---|---|
| **做法** | `runs/<run>/raw/` 只写一次、永不修改；normalized / claims / judgments / scores 全部可由 raw 重跑 |
| **为什么** | 这是"改评分口径不用重跑模型"的唯一实现方式。只要原始回复还在，任何规则变更都能回溯 |
| **代价** | 存储会随时间增长（但全是文本，10 项目 × 5 候选 ≈ 几 MB，可忽略） |
| **缓解** | raw 进 git；每季度归档一次 zip |
| **落点** | `raw/` 目录约定（v0.1 已实现，见 `02_总体架构.md` 第三节） |

### 决定 3：双盲靠程序，不靠提示词

| 项 | 内容 |
|---|---|
| **做法** | ① 匿名 ID 用**本地随机盐 + HMAC**生成，不可反推 ② `pool.jsonl`（给裁判看）与 `origin.jsonl`（映射）物理分离 ③ 裁判包里不含来源、不含支持度 ④ 裁判不得是参赛者 ⑤ 支持度按 vendor 去重 |
| **为什么** | 提示词写"请不要偏袒"没有任何约束力；只有"裁判输入里根本没有这个字段"才是硬保证 |
| **代价** | 无法做"某模型 vs 某模型"的两两对比分析（因为不知道谁是谁）；需要额外的映射表管理 |
| **缓解** | `origin.jsonl` 保留完整映射，分析时在本地 join，不出报告 |
| **落点** | `pipeline.make_packets`（v0.1 已实现）+ 本方案新增的盐哈希与作者混淆档位（`05`） |

### 决定 4：可复用性由"沉淀题库"承担，不是由"历史 run"承担

| 项 | 内容 |
|---|---|
| **做法** | 第一批模型交叉复核出的每条真/假判断，落进 `bank/<proj>_bank.jsonl`，带 `issue_id`、`verdict`、`real_sev`、`found_by[]`。新模型来了先**撞库**，命中即得分，只对未命中的新疑点做增量盲评 |
| **为什么** | 历史 run 只能回答"上次谁得了多少分"，回答不了"这条 bug 到底是不是真的"。而后者才是可复用的资产 |
| **代价** | 题库需要维护（合并、拆分、平反、作废）；`issue_id` 一旦不稳定，历史分数就会乱 |
| **缓解** | `issue_id` 用 `proj + 文件 + 主行号 + 类别` 生成，行号漂移时靠撞库规则兜底（见 `06` 第五节） |
| **落点** | 新增 `src/bank.py`（v1.0 核心） |

### 决定 5：双阶段评分，冷启动不假装精确

| 项 | 内容 |
|---|---|
| **做法** | **阶段 A（冷启动）**：绝对分 = Σ(命中×严重度权重) − 误报×0.5 + 独到加成，只在本次 run 内可比。<br>**阶段 B（题库成型）**：率化分 = 100×(0.7×Rw + 0.2×P + 0.1×C) − 2F − 4Fh − 5T + U，可跨 run 可比。<br>切换条件：`bank` 已确认问题数 ≥ 20 且覆盖率 ≥ 0.8 |
| **为什么** | 率化分的核心是 Rw（加权召回率），分母是"已知问题总权重"。冷启动时这个分母不存在，硬算就是拿"模型发现的并集"当分母——那等于假设"模型没发现的不存在"，召回率会虚高到 90%+，是假精确 |
| **代价** | 两套分数并存，读者要理解"为什么有两个数" |
| **缓解** | 报告里用两列并排 + 一行脚注说明；`scores.json` 里两套都存，字段名区分 `raw_score` / `rate_score` |
| **落点** | `pipeline.score` 扩展 + `report` 双列（见 `07`） |

## 四、版本路线

| 版本 | 一句话 | 关键能力 | 状态 |
|---|---|---|---|
| **v0.1** | 把流程跑通 | 16 命令、8 字段、三级裁决、可执行复现、demo | ✅ 已完成 |
| **v0.2** | 让分数站得住 | 盐哈希 ID、六类裁决标签、顺序双评、埋点题库（inject）、并列判定 | 待做，约 6 张任务卡 |
| **v0.3** | 让采集不痛苦 | API 自动采集、精确 token、按会话过滤耗时 | 待做，依赖 API 可用性 |
| **v1.0** | 让历史不浪费 | `issue_bank` 沉淀、撞库、增量盲评、率化分、趋势图 | 待做，是本方案的重心 |

版本之间的依赖关系：

```
v0.1 ──→ v0.2 ──→ v1.0
           └──→ v0.3（可与 v0.2 并行，不阻塞）
```

**不要跳级**：没有 v0.2 的六类标签和顺序双评，v1.0 的 `bank` 会沉淀一堆"说不清真假的条目"，题库越用越脏。

## 五、成功判据

跑完第一轮（10 项目 × 4 候选），用这五条判断这套系统值不值得继续投入：

| # | 判据 | 合格线 | 怎么测 |
|---|---|---|---|
| S1 | **能修 bug** | 一审结果里至少 15 条被确认，且其中 ≥5 条是你之前没发现的 | 人工过一遍 `bank`，数 `verdict=true` 且 `found_by` 不含你自己的条目 |
| S2 | **能区分** | 4 个候选的终分极差 ≥ 15%（不是全部挤在 ±3 分内） | 看 `scores.csv` 的 `final_score` 列 |
| S3 | **能复现** | 同一候选同一项目跑两次，分差 ≤ 10% | 抽 2 个项目做 repeat=2 |
| S4 | **能复用** | 加第 5 个模型时，撞库命中率 ≥ 65%，增量盲评条目 ≤ 30 条 | 看 `bank` 的 `hit_rate` 统计 |
| S5 | **能解释** | 任取一条扣分，能在 3 分钟内说清"扣在哪一层" | 从 `scores.json` 反查到 `verdicts.jsonl` 再到 `raw/` |

如果 S1 不达标，说明题库太干净或提示词太松，先修题库；如果 S2 不达标，说明候选同质化（都是同一家族），换候选；如果 S3 不达标，说明单次噪声大于真实差异，需要 repeat≥2 或增大题库。

## 六、成本预算

| 项 | 估算 | 说明 |
|---|---|---|
| 一评审阅时间 | 10 项目 × 10 分钟 ≈ 100 分钟 | 不含人工复核 |
| 人工复核 | 15–25 条 × 2 分钟 ≈ 40 分钟 | 只过"独到发现 + P0/P1 争议" |
| 裁判调用 | 每条 claim 3 票 × 约 200 条 × 3 项目 ≈ 1800 次短调用 | 按各家 API 价格，约 10–30 元 |
| 存储 | 每 run 约 2–5 MB 文本 | 一年 20 run 也就 100 MB |

**真正的成本是前两项（人的时间），不是 token。** 所以方案里所有"自动化"的优先级，都按"能省人多少分钟"排序，而不是按技术优雅度排序。

## 七、这份方案不解决什么

写在前面，避免期待错位：

1. **不解决"所有模型都漏掉的 bug"。** 这是交叉验证的结构性盲区，只能靠埋点、真实使用中的 bug 回流、定期人工审计逐步补。见 `10` 第二节。
2. **不解决"产品能力"与"模型能力"的分离。** 一个带索引、能跑工具的产品，天然比纯对话强。要分离只能自己拼上下文、禁工具，那是另一套实验设计。
3. **不解决"绝对排名"。** 10 个项目的样本量给不出"某模型比某模型强 3.2%"这种结论，只能给分档（第一梯队 / 第二梯队 / 待观察）。
4. **不解决"未来版本的预测"。** 测的是当下这次组合，不是模型的潜力。
