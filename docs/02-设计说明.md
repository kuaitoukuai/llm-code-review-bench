# 设计说明：为什么这样搭，以及它在哪里会失灵

> 这份文档解释每个设计选择的理由，以及三条前提假设各自站不站得住。
> 改系统之前先读这里，能省掉很多返工。

---

## 一、先说清楚三条前提假设

你在需求里列了三条假设。逐条检验：

### 假设一：大模型判断正确率超过 50%，多次交叉验证可以提高正确率

**前半句成立，后半句有条件。**

多数投票提高正确率，数学上依赖 Condorcet 陪审团定理，它有个硬要求：**每个投票者的正确率必须显著高于 50%**。次数不是万能的——p 越接近 0.5，需要的票数越接近无穷。

粗略估算（三票多数）：

| 单模型正确率 | 三票多数后 | 增益 |
|---|---|---|
| 0.50 | 0.50 | **零** |
| 0.60 | 0.648 | +4.8 pt |
| 0.70 | 0.784 | +8.4 pt |
| 0.80 | 0.896 | +9.6 pt |

所以"多个模型交叉验证"在 p≈0.5 时**完全没有增益**，只是三个硬币。

这条定理还有第二个前提：**错误必须相互独立**。同族模型共享训练语料与对齐偏好，会犯同一个错。三个 DeepSeek 变体投票，等价于一个 DeepSeek 投三票。

→ 系统的对策：支持度按 `vendor` 去重，不按模型数。这一条在 `pipeline.cluster` 里。

### 假设二：同族给高分存在，但不会太严重

**这条基本成立，代价可以量化。**

公开实测的同族裁判一致率虚高约 5–7 个百分点，自我偏爱在 16%–30% 区间。不算致命，但足以在势均力敌时改变排序。

→ 系统的对策：裁判包里不含来源信息（双盲的一半），并建议裁判不选参赛模型（另一半）。人工裁决永远优先于机器票。

### 假设三：能言善辩、巧舌如簧，交叉验证可以避免大部分

**这条只对一半。**

交叉验证能过滤"只有一家这么说"的花言巧语，但过滤不了"多家都用同一套话术"——而那恰恰是训练语料同质的必然结果。

真正的防线不是投票，是**压缩自由发挥的空间**。所以提示词里做了三件事：固定 8 个字段、4 个字段带硬字数上限、超限整条拒收。模型没地方写"综上所述，这是一个值得关注的问题"。

代价是：短字段也会压掉一部分真实信息。这是刻意的交换——宁可漏掉表述细节，也不能让字数成为分数的来源。

## 二、数据分五层，只有第一层不可变

这是整套系统最重要的结构。它决定了"以后改评分口径，历史数据依然可用"能不能成立。

| 层 | 位置 | 内容 | 可变性 |
|---|---|---|---|
| **原始层** | `runs/<run>/raw/` | 模型原始回复，逐份保存 | **不可变**。改了就没有可比性 |
| **归一化层** | `normalized/` | 统一字段后的一条条发现，每行一条 | 可重跑（提示词或解析规则变了才需要） |
| **匿名层** | `claims/pool.jsonl` + `origin.jsonl` | 前者给裁判看（无来源），后者存映射 | 可重跑 |
| **裁决层** | `reproductions/` + `executions/` + `judgments/` | 复现测试、执行日志、packets / votes / human / verdicts | **随时可补**。人工判完直接重算 |
| **计分层** | `scores.json` | 算出来的分 | 可任意重算 |

关键性质：**裁决层的任何补充，只触发计分层重算，不碰原始层。**

所以你可以三个月后回来说"上次那个错判我改主意了"，改一行 `human.jsonl`，重跑两条命令，全部分数更新，模型不用重跑一次。

### 为什么 pool 和 origin 要分成两个文件

你要的"双盲"和"答案一行一行另存，避免看到抄答案"，靠这个实现：

- `pool.jsonl`：`claim_id` + 内容，**没有 candidate 字段**。裁判包只从这里取。
- `origin.jsonl`：`claim_id → candidate/task/repeat` 的映射，并记录可选复现测试的位置。执行与计分脚本读，裁判包不读。

裁判拿到的包里，看到的是一条匿名声明加一段代码。它没法知道这是谁说的，也没法知道有几个人说过——支持度信息也不放进包里，避免"这么多人都说了，那应该是对的"这种从众偏差。

## 三、七个关键设计决策

### 1. 不做加权总分合成

能力和成本之间没有客观换算率。硬加权出一个"综合分"，等于把一个价值判断伪装成客观指标。

所以：**主榜按终分排序，成本单列成轴**，散点图让你自己看取舍。

### 2. 误报扣 0.5，不是 1

漏掉一个真 bug 的代价，高于多看一个假的多花两分钟。这个比例是价值判断，你可以调。

反过来，如果误报扣分设成 2，模型的最优策略会变成"只说最有把握的那一条"——召回崩掉。

### 3. 独到命中权重翻倍

这是全系统最有争议的一个设定，也是最能反映你需求的一个。

调研数据显示，业界最严谨的评审基准里，53% 的金标准来自 LLM 产出。这意味着**提出一个所有模型都没提的真问题，反而更容易被判为假**。

不加这条，系统会系统性杀掉最有价值的发现。加了这条，代价是幻觉条目也会被加分——所以独到发现必须走人工复核或执行验证，不能只靠共识推断。

### 4. 报不足 3 条按误报补齐

不设这条，博弈的最优解是"一条不报"，得分零、成本零、还显得很谨慎。

代价是：真的没问题的代码，模型也会被迫报够 3 条。所以这个值应该按你的题库质量调——如果大部分题目确实有 3 个以上真问题，就保留；如果题目偏干净，改成 2 或 1。

### 5. 时间只扣 5%，且从中位数起算

你要求"以正确率为主"，所以时间不能改变排名，只能打标。

从**全局中位耗时**起算而不是固定秒数，是因为不同题目的绝对耗时差很多（文件数、行数）。用相对值才公平。

代价：时间系数实际上很少生效。这是设计意图，不是 bug。

### 6. 聚类按「文件 + 行号窗口 + 标识符」三重判定

最初的实现只按「文件 + 行号窗口 8 + 类别」聚类，实测会把**相邻两行的两个不同 bug 合成一条**：

```
14  return total / len(items)      ← 除零
18  return order.items[0]["name"]  ← 空列表越界
```

差 4 行，同类别，被合并。两个真 bug 算成一条，所有候选都少拿分。

修正后加了两条规则：
- 与**组首元素**比较（不是与最后一个），消除"14↔15↔18 三跳连成一簇"的链式传递
- 行号差超过 3 时，要求两边的 snake_case 标识符（通常是函数名）有交集

第二条能分开 `average_price` 和 `first_item_name`，但分不开两个都叫 `process` 的函数。**聚类永远是近似的**，所以人工复核队列里会附原始描述。

### 7. 严重度只排序，不进权重计算

严重度是同类评测里最不稳定的维度——同一个 bug，不同模型给的档位能差两级。

所以：严重度只用来（a）算加权命中分，（b）决定哪些条目进人工队列。**不用来判定"这条是否成立"**。裁判只回答"这个 bug 存在吗"，不回答"它多严重"。

## 四、它在哪里会失灵

诚实列出，别指望它包治百病。

| 场景 | 后果 | 现状 |
|---|---|---|
| **裁决覆盖不全** | 只有能写成标准库 Python 测试的发现才能使用执行证据 | v0.2 已加可执行裁决，其余仍靠人眼和裁判票 |
| **执行安全** | 模型生成的测试本身是不可信代码 | 独立目录、精简环境、超时与显式授权；仍不是安全沙箱 |
| **测试质量** | 测试通过不代表声明必然为假，失败也可能来自错误测试 | 导入错误不采信，冲突进人工队列，人工结论优先 |
| **错误相关** | 同族模型犯同一个错，共识推断会把它当真相 | 已用 vendor 去重缓解，但没根治 |
| **裁判圈子闭环** | 作答与裁判都是同一批主流模型，共享偏好 | 只能靠人类裁判抽检校准 |
| **聚类误合并/误拆分** | 两个 bug 算一条，或一个 bug 算两条 | 人工复核时可见，可修正 |
| **产品与模型未分离** | 测的是"产品+模型"组合能力 | 你的需求如此，报告里已标注 |
| **token 记录不准** | 输入 token 各家口径不同，成本轴不可横比 | 散点图明确标注"只作参考" |
| **单次噪声** | 只跑一次时 10% 以内的差距无意义 | 建议至少两次 |
| **题库偏见** | 题目都是你写的代码，模型可能对某类风格更熟 | 这是自建题库的固有代价 |

## 五、版本演进

**v0.2（已实现）**
- `review_v2` 允许每条发现携带一个标准库 `unittest` 复现文件
- `execute` 在冻结代码的独立副本中运行测试：跑红复现、跑绿未复现，导入错误与超时不作为结论
- 裁决优先级变为人工 > 执行结果 > 模型票 > 共识；冲突结果进入人工队列
- 当前只支持 Python，后续应在真实容器隔离中扩展其他语言

**v0.3（已实现）**
- 根目录 `启动.txt` 驱动有文件与终端工具的模型一次完成 10 项目评测
- `prepare --expected 10` 批量冻结或复用题目，保证不同候选使用相同代码
- `register-candidate` 登记模型身份，固定 `agent-10` 批次支持不同时间续跑
- 原始结果逐题落盘，已完成题目跳过，不读取其他候选答案

**v0.4（下一步）**
- API 自动采集：对支持 API 的候选，跳过 agent 手工写文件，自动记录精确的 token 与耗时
- 同时解决"输入 token 不可比"的问题——自己拼上下文，输入完全固定

**v1.0**
- 多 run 趋势：同一批题在模型版本迭代下的分数漂移
- 需要题库版本化（task 的 files.jsonl 已带 sha1，够用）

## 六、一句话总结

这套系统的价值不在于给出一个精确排名——20 道题给不出精确排名。

它的价值在于：**每一次结论都能追溯到一条具体的裁决，每一条裁决都能被推翻重算，而推翻重算不需要重跑模型。**
