# 调研笔记：代码能力评测这件事，别人踩过哪些坑

> 目的：说明本系统的每个设计选择分别对应哪条实证。不是文献综述，是取舍依据。
> 数据来源标注为「公开披露」的，来自项目官方文档或技术博客；标注「实测」的，来自第三方复现。

---

## 一、为什么不能直接用公开榜单

### 1.1 三个主流基准测的不是同一件事

| 基准 | 测什么 | 本项目是否适用 |
|---|---|---|
| SWE-bench Verified | 在真实仓库里修 GitHub issue，跑测试验证 | 不适用：题目是别人的仓库、别人的技术栈 |
| LiveCodeBench | 竞赛题，持续更新抗污染 | 不适用：算法题与业务代码的故障模式几乎不重叠 |
| Terminal-Bench | 终端里的多步 agent 任务 | 不适用：测的是工具编排，不是读代码 |

更麻烦的是，同一时期不同来源对同一模型的 SWE-bench Verified 得分能差出十几个百分点，原因包括 harness 版本不同、是否声明训练数据污染、是否厂商自报。这些数字不能直接横比。

### 1.2 结论

榜单能告诉你"这个模型大概在什么档位"，告诉不了"它在我这套 FastAPI + React + SQLite 的代码上能不能找出我自己会踩的坑"。后者只能自己测。

## 二、四个直接对口的开源项目

### `review-bench/ReviewBench`（GitHub 官方，2026-10 发布，MIT）

目前最严谨的 AI 代码评审基准。

| 项 | 数据 |
|---|---|
| 规模 | 219 个 PR，187 个仓库，19 种语言 |
| 抽样基础 | 分析 1.039 亿条真实 PR 后按分布抽样 |
| 金标数量 | 全量集 2,623 条真阳性发现 |
| 标注方式 | 人类评审意见 + 作者后续修复提交 + 静态工具 + 多家前沿模型，语义去重后按统一量规判定 |
| 复判一致性 | 资深工程师独立复判全部真值，一致率 96.6% |
| 指标 | grounded precision/recall/F1（只算已知标签）+ augmented 指标（金标之外的有效发现也计分） |

**最该注意的一点**：公开数据显示，其真阳性发现中 **53.0% 由 LLM 评审代理产出、45.2% 由 Copilot 产出，来自人类评审意见的仅 1.5%**。

这不是这个项目做得不好，恰恰说明现实就是如此——人类评审意见太稀疏。但它带来一个副作用：用它当金标准，等于奖励"和那些模型风格相似"的输出。一个模型如果提出了那些模型都没提的真问题，反而会被判为假阳性。

→ 本系统的对策：**独到发现单独开一条通道，不走多数票否决**，并给权重翻倍。

### `ironbee-ai/code-review-benchmarks`（MIT）

21 个模型 × 最多 3 个思考档位 × 3 次重复 = 7,980 次评审，跑在 Martian Code Review Bench 上。harness、提示词、每一次回复、每一张裁判票、每一笔成本全部开源。

它提供了本系统最需要的三个数字（见下一节）。

### `withmartian/code-review-benchmark`（MIT）

50 个真实 PR（Sentry、Grafana、Keycloak、Cal.com、Discourse），配 **173 条经人工核对的 golden 意见**。

规模最小，但标注是人做的，污染程度低于同类。如果要引入公开语料做泛化检验，优先用这个。

### `promptfoo`（MIT）

通用多模型评测框架，YAML 声明式，`npx` 起步。适合快速验证"某个提示词在多个模型上的表现"。

本系统没有基于它，原因是：它的抽象是「提示词 × 测试用例 × 断言」，而这里需要的是「匿名化 → 去重 → 支持度 → 多级裁决」这条链路，属于数据流水线而非提示词评测，套进去反而绕。

## 三、几个会毁掉结论的数字

以下均来自 ironbee 的公开实测（50 个 PR，三次重复）：

| 现象 | 数据 | 对本系统的含义 |
|---|---|---|
| **单次结果不可信** | 同一配置三次重复之间，F2 中位波动 2.6 分，个别配置波动 7.5 分 | 只跑一次时，10% 以内的差距不能当结论 |
| **堆思考档位不一定更好** | 最高档下，18 个模型里 13 个召回显著上升，但 11 个精确率显著下降 | 「更努力」通常变成「报得更多」，不是「报得更准」 |
| **版本新不等于更强** | Claude Opus 5 在低档与 Opus 5.5 持平，价格却是 1.6 倍；Sonnet 5 在所有档位都落后 Sonnet 5.5 12–31 分 | 别假设"最新的一定最好"，要测 |
| **成本差异巨大** | 单次全量 pass（约 2,060 次评审）作答约 350 美元，判分再 280–330 美元 | 判分成本与作答成本同量级，这是"全自动裁判"必须面对的账单 |

另有一条来自其「假阳性审计」的发现：**被判为假阳性的条目里，约三分之一其实是有用的发现**。也就是说，precision 是被低估的。

→ 本系统的对策：报告的"覆盖度"标为 proxy，并在人工复核时给出原始描述，不只看机器判定。

## 四、LLM 当裁判的六种偏差

这些是学界与工程界的共同结论，不同来源给的量级略有差异，取区间：

| 偏差 | 表现 | 量级 | 缓解手段 |
|---|---|---|---|
| **位置偏差** | 同一对答案换个顺序，判决就变 | 代码类两两比较可达 10 个百分点以上，部分模式影响 40% 的评估 | 双向交换，只采纳两次一致的结论 |
| **冗长偏差** | 偏好更长、更详细的回答 | 影响 10–15% 的准确率 | 限条数 > 限字数；不因报告长而加分 |
| **自我偏爱** | 给自己或同族的输出打高分 | 实测 16%–30% | 裁判不得是参赛者；跨族 |
| **同族偏高** | 同一训练家族的裁判一致率虚高 | 5–7 个百分点 | 按 vendor 去重算支持度 |
| **立场偏差** | 答案语气自信就被判为更对 | 无统一量级，但可复现 | 强制结构化字段，压缩自由发挥空间 |
| **裁判幻觉** | 裁判自己编造理由 | 在领域外尤其明显 | 只让它判"是否成立"，不让它判"有多严重" |

另有一条经验值：**LLM 裁判与人类专家的一致率，在专业领域通常落在 60%–68%**。所以裁判票只能当"第二等证据"，不能当真相。

→ 本系统的对策：四级裁决（人工 > 执行结果 > 模型票 > 共识推断），并且**明确标注每条结论的证据强度**，不混成一个分数。

## 五、这些发现怎么落到系统里

| 调研结论 | 系统里的对应设计 | 在哪看 |
|---|---|---|
| 金标准可能被模型污染 | 不用现成答案；真相来自人工/执行/裁判/共识四级 | `judgments/verdicts.jsonl` 的 `confidence` 字段 |
| 独到发现会被多数票杀掉 | `support_count == 1` 且判为真 → 权重翻倍 | `config/system.toml` 的 `unique_bonus` |
| 单次结果方差大 | 支持同题多次重复，结果合并统计 | `start/done` 的 `--repeat` |
| 报得多 ≠ 报得准 | 主指标是加权命中减误报，不是条数 | `scores.csv` 的 `final_score` |
| 不报最省事 | 报不足 3 条按误报补齐 | `weights.min_findings` |
| 位置偏差 | 单条独立裁决，不做"三份报告谁更好"的成组比较 | `packets` 每个包只含一条 claim |
| 同族偏高 | 支持度按 vendor 去重 | `pipeline.cluster` |
| 冗长偏差 | 每条 8 个字段，4 个有硬字数上限，超限整条拒收 | `normalize` 的拒收统计 |
| 裁判不可信 | 裁判票只算"第二等证据"，人工永远优先 | `pipeline.adjudicate` |
| 时间与成本是真实约束 | 时间系数轻微扣分，成本单列不进主分 | `scatter.html` |
| 版本迭代快 | run 目录留全部原始数据，可重算 | `runs/<run>/` |

## 六、仍未解决的两件事

1. **执行覆盖与安全边界。** v0.2 已支持 Python `unittest` 可执行裁决，但外部依赖和其他语言仍未覆盖。独立目录也不是安全沙箱，模型生成的测试必须先审查；高风险场景应使用容器或一次性虚拟机。
2. **裁判圈子闭环。** 参与作答和参与裁判的都是同一批主流模型，共享相似的训练语料与偏好。唯一的破局是引入人类裁判做校准，哪怕只判 20 条，也能测出"机器裁判和你的判断差多远"。
